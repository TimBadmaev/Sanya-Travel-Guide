# Итерация 8 — «Время + интерес + нагрузка»: результат реализации

Вторая функциональная часть Итерации 8 (`PRODUCT.md`, строка 8 таблицы 11.2, `ITERATION-8-NEARBY-IMPLEMENTATION-RESULT.md` §Next steps п.3). «Рядом со мной» (первая часть) не менялась. Расширение базы мест (третья часть строки 8) в эту задачу не входило и не выполнялось.

## Implementation summary

На экране «Места» (`#/places`) добавлен подборщик: пользователь выбирает **сколько у него времени**, **что ему интересно** (category) и, опционально, **нагрузку** (effort), нажимает «Подобрать» — и видит тот же список мест, что и обычные фильтры-чипы, просто предзаполненный нужными токенами.

Никакой отдельной системы рекомендаций не создано. Подборщик не считает score, не ранжирует и не оценивает места — он только выбирает 1–3 готовых токена и передаёт их в уже существующий механизм `f=` (`parseFilters` → `applyFilters` → `sortByDistance` → `renderPlaceRow`), тот же, что обслуживает обычный ряд чипов. Цепочка ровно такая, как в задании:

`verified places → фильтр по времени → фильтр по интересу (category) → опционально фильтр по effort → существующая сортировка → существующий рендер (renderPlaceRow)`.

## User flow

1. Пользователь открывает «Места» (`#/places`) — как обычно.
2. Под блоком «Рядом со мной» видит кнопку «🎯 Подобрать по времени и интересу».
3. Открывает форму: выбирает один вариант времени (обязательно), один вариант интереса (обязательно), при желании — один вариант нагрузки (необязательно, по умолчанию «Любая нагрузка»).
4. Кнопка «Подобрать» недоступна, пока не выбраны и время, и интерес.
5. По нажатию форма сворачивается, список ниже — обычный список мест с применёнными фильтрами, счётчик «Найдено N», обычные карточки.
6. Если результатов нет — обычное пустое состояние с подсказкой, какой фильтр снять (существующий `suggestFilterToRemove`).
7. Плашка «Подбор: …» показывает применённые время/нагрузку (интерес виден и так — соответствующий чип в общем ряду подсвечен), с кнопкой «Сбросить подбор».

## Available filters

**Время** (`config.json` не используется — правило вшито в код, т.к. `durationHours` не справочник):

| Кнопка | Правило |
|---|---|
| До 2 часов | переиспользован существующий флаг `short` |
| До 3 часов | новый флаг `medium3h` |
| Полдня и больше | без токена — верхнего порога нет |

**Интерес** — 6 значений из `config.json → categories`, без изменений: Пляжи, Природа, Культура, Развлечения, Рынки, Покупки. Тэги (`view`, `sunset`, `kids`, `photo`, `island`, `local`) в подборщик не добавлены отдельным полем — по заданию это делает избыточную развилку интерфейса, а категория уже даёт ту же самую формулировку интереса, что и существующие сценарии Главной («Хочу природу» и т.п.).

**Нагрузка** (`effort`, необязательно):

| Кнопка | Правило |
|---|---|
| Любая нагрузка (по умолчанию) | без токена |
| Лёгкая нагрузка | переиспользован существующий флаг `easy` (`effort === "low"`) |
| Средняя нагрузка | новый флаг `moderate` (`effort === "medium"`) |

Кнопки «Высокая нагрузка» нет: среди 18 текущих verified мест (`data/places.json`) нет ни одного с `effort: "high"` — 14 `low`, 4 `medium`, 0 `high`. Добавление такого чипа сейчас означало бы кнопку, которая при любой комбинации с другими параметрами гарантированно даёт 0 результатов; появление первого verified места с `effort: "high"` — повод для отдельного, явного решения о чипе, а не автоматическое расширение.

## Time rule

Правило детерминированное и одно для всех трёх вариантов, включая уже существующий `short` (`PRODUCT.md` 8.4): **пользователь указывает максимум доступного времени** (а не окно), и место подходит, если минимально нужное ему время (`durationHours[0]`) не превышает выбранный порог. Верхняя граница `durationHours[1]` в фильтрации никогда не участвует — как и во всём остальном приложении (D-21/9.2 не подразумевает диапазонной проверки).

Пример из задания: место с `durationHours = [2, 4]` при выборе «до 3 часов» **проходит** фильтр (`2 ≤ 3`), при выборе «до 2 часов» — **не проходит** (`2 ≤ 2` — тоже проходит, если durationHours[0]=2; не проходит только при durationHours[0] > 2, например `[3,5]`).

Этот вариант («максимум времени», не «окно») выбран, потому что именно так уже работает единственный существующий времязависимый чип «До 2 ч» (`FLAG_PREDICATES.short`, `PRODUCT.md` 8.4) — вводить второе, отличающееся правило для тех же данных значило бы иметь два несовместимых определения «времени» в одном приложении.

## Interest rule

Один выбранный `category` id передаётся как обычный токен категории — работает та же логика `applyFilters()`, что и у ручных чипов категорий (категории внутри одной группы объединяются через ИЛИ, но здесь выбор всегда ровно один, так что это не имеет практического значения). Никакой новой сортировки или веса у категорий нет.

## Effort rule

Аналогично: `easy`/`moderate` — обычные AND-флаги того же `applyFilters()`. «Любая нагрузка» просто не добавляет токен.

## Interaction with existing filters

- **Обычные чипы категорий/флагов** — не тронуты, работают как раньше (мгновенно, без навигации). Подтверждено регрессией.
- **Подбор — замена, не слияние.** Нажатие «Подобрать» устанавливает `tokens` целиком в `[время?, интерес, нагрузка?]`, отбрасывая то, что было выбрано чипами до этого. Это предсказуемее, чем тихо объединять с прежним состоянием.
- **После подбора обычные чипы продолжают работать** — можно снять категорию или добавить «С детьми»/«Бесплатно» поверх результата подбора; чип категории в общем ряду показывает нажатое состояние, потому что это тот же токен.
- **`near=1`** (сценарии Главной, «Рядом со мной» через точку проживания) и подбор — независимы (раздел 10 задания) и просто складываются: `near` ограничивает базовый список радиусом, подбор дальше фильтрует его теми же токенами `f=`. Проверено: обе плашки («Расстояния — …»/радиус и «Подбор: …») показываются одновременно, список — пересечение условий.
- **«Рядом со мной» (геолокация)** — отдельный блок, физически выше подборщика, не связан с ним по коду и данным.
- **`addTo` (выбор места для дня плана)** — не затронут, `renderPlaceRow(..., addTo)` вызывается как раньше.
- **Избранное (`f=saved`)** — не затронуто, отдельный существующий флаг.
- **Draft места** — никогда не участвуют: подбор работает над тем же массивом `places`, который `loadPlaces()` уже отфильтровал по `status: "verified"` (D-18); отдельной проверки не потребовалось.

## Validation

### Логика

Проверено headless Chrome 152 (ручной CDP-клиент на stdlib Python, см. память проекта), `scratchpad/val_picker.py` — **36/36** проверок:

- Форма показывает ровно 3 группы («Сколько у вас времени?», «Что вам интересно?», «Нагрузка (необязательно)») с правильными вариантами (3 / 6 / 3).
- «Подобрать» недоступна, пока не выбраны время и интерес; доступна после выбора обоих (нагрузка не обязательна).
- **Время + интерес** («До 3 часов» + «Природа») → 4 места (`durationHours[0] ≤ 3` среди 6 verified-мест категории `nature`), результаты — обычные карточки, draft-места (`bohou-village`, `linchunling-forest-park`) не попадают.
- Главный чип категории («Природа») показывает нажатое состояние после подбора — тот же токен.
- Обычная карточка места открывается по клику, `history.back()` возвращает на «Места».
- **Интерес + нагрузка** без ограничения по времени («Полдня и больше» + «Природа» + «Средняя нагрузка») → 4 места (пересечение `nature` и `effort: "medium"`); URL не содержит `medium3h`/`short` (верхнего порога нет).
- **Пустой результат** («Покупки» + «Средняя нагрузка» — среди verified такого сочетания нет) → «Найдено 0», подсказка предлагает снять именно «Средняя нагрузка» (`suggestFilterToRemove`), снятие через подсказку убирает `moderate` из URL и синхронно убирает плашку «Подбор: …», не оставляя её висеть с устаревшим токеном.
- Прямая загрузка `#/places?f=nature,medium3h,moderate` сразу показывает плашку «Подбор: До 3 часов · Средняя нагрузка» (без предварительного нажатия «Подобрать» в этой сессии) — состояние вычисляется из URL, а не из памяти виджета.
- «Сбросить подбор» снимает `medium3h`/`moderate`, не трогая категорию `nature` (обычный чип остаётся нажатым).
- **`near=1` + подбор одновременно**: без точки отсчёта `near=1` молча игнорируется (как и раньше); с точкой отсчёта (эмулирован `stg:trip.area="yalong"` + `stay` через spot) обе плашки («радиус» и «Подбор: …») показываются вместе, список — пересечение условий; «Сбросить подбор» не убирает `near=1`.
- Нет горизонтальной прокрутки на 320×568 с открытой формой подборщика.
- Console errors / необработанные исключения за весь прогон — не зафиксировано.

## Known limitations

- **Малое число и разнообразие verified мест ограничивают полезность подборщика.** При 18 verified местах многие сочетания «время + интерес + нагрузка» дают 0–2 результата (например, «Покупки» — всего 1 verified место вообще, любое сочетание с нагрузкой ≠ «Любая» и не «Лёгкая» даёт 0). Это не ошибка логики, а честное отражение текущего объёма базы (D-05 — цель 25–40 мест).
- **Порог «До 3 часов» — единственный новый содержательный уровень.** Третий уровень «Полдня и больше» при текущих данных эквивалентен «без ограничения по времени» (максимум `durationHours[0]` среди verified мест — 4 ч), потому что явного признака «многочасовая поездка» (например, выезд на целый день, `wuzhizhou-island`/`nanshan-cultural-zone`) в схеме нет — только нижняя граница диапазона. Это не считается недостатком реализации: правило детерминированное и честно отражает то, что реально есть в данных.
- **Тэги как отдельная ось «интереса» не реализованы.** `view`/`sunset`/`kids`/`photo`/`island`/`local` пока может выбрать только через существующие чипы `kids`/категории, не через подборщик — решение осознанное (см. «Available filters»), не пробел, который забыли закрыть.
- **`bestTime`** (произвольный текст) не участвует в подборе — как и раньше, это не структурированное поле (D-21), автоматически сопоставлять его с выбранным временем нельзя без выдумывания правил.
- **Время в пути не учитывается** — как и везде в приложении (X-12, D-11): подбор находит места по `durationHours`, но не считает, сколько до них добираться.
- **Плашка «Подбор: …» видна только для двух «невидимых» токенов** (`medium3h`, `moderate`); выбранная категория интереса не дублируется в этой плашке — она уже видна как нажатый чип в общем ряду. Если пользователь вручную снимет этот чип, отдельного предупреждения «вы больше не подбираете по интересу» не будет — это тот же чип, что и всегда, ведёт себя как обычно.
- **Подбор — полная замена набора фильтров**, а не слияние с уже выбранными вручную чипами. Если это неудобно для сценария «уже стоит „Бесплатно“, хочу дополнить подбором» — потребуется отдельное решение владельца, сейчас предсказуемость важнее.

## Next steps

Только рекомендации, самостоятельно не реализовывались:

1. По мере роста базы мест (D-05, 25–40) переоценить, не появился ли смысл в отдельном пороге «весь день» (например, `durationHours[0] > 4`) и в чипе «Высокая нагрузка» — оба сейчас не введены из-за отсутствия данных, а не из-за ограничения архитектуры.
2. Проверить на реальном iPhone, Chrome (Android), Яндекс Браузере — как и предыдущая часть Итерации 8, здесь не проверялось.
3. Третья часть строки 8 таблицы 11.2 PRODUCT.md — расширение базы мест — не входила в эту задачу и не начиналась.
4. Если владелец решит, что подбор должен дополнять, а не заменять уже стоящие вручную фильтры — обсудить и зафиксировать точное правило слияния отдельным решением (сейчас сознательно не реализовано, см. «Known limitations»).
