## 4. `stg:trip` — что хранится [пункт задания 2, 14]

### 4.1 Формат

Схема из `PRODUCT.md` 9.7 не расширяется:

```json
{ "start": "2026-11-05", "end": "2026-11-19", "area": "yalong" }
```

| Поле | Тип | Значение «не задано» | Комментарий |
|---|---|---|---|
| `start` | строка `YYYY-MM-DD` | `null` | Дата начала поездки |
| `end` | строка `YYYY-MM-DD` | `null` | Дата окончания поездки |
| `area` | строка — `id` из `config.areas` | `null` | Район проживания; допустим `"other"` |

**Сам факт наличия ключа `stg:trip`** (даже со всеми `null`) означает, что экран первого запуска уже показывался — отдельного флага не заводим **[I3-1]**. Это позволяет не расширять схему `PRODUCT.md` 9.7 и не менять `SCHEMA_VERSION`.

### 4.2 Чего в `stg:trip` быть не должно

| Не хранить | Где живёт на самом деле |
|---|---|
| Фильтры списка мест | В URL (`#/places?f=…`), foundation §3.3, `PLACES-IMPLEMENTATION.md` §11 |
| Избранное | `stg:saved` |
| Прогресс чек-листа | `stg:checklist` |
| Раскрытые этапы «Подготовки» | Модульная переменная `prepare.js` |
| Посчитанные расстояния, отсортированный список, «сегодня» | Ничего не кэшируется: считается при рендере из `places.json` + `config.json` + `stg:trip` **[I3-2]** |
| Название/координаты района | Только `id`; имя и `center` всегда берутся из `config.json` (D-20) **[I3-3]** |

### 4.3 Чтение: защита от испорченных и устаревших значений

`storage.js` уже задаёт образец (`getSavedIds()`): повреждённое значение не ломает экран. Те же правила для поездки:

| Ситуация | Поведение при чтении |
|---|---|
| Ключа нет | `{ start: null, end: null, area: null }` + признак «первый запуск» |
| JSON повреждён / не объект | То же, что «ключа нет», + `console.error`; ключ **не** перезаписывается автоматически **[I3-4]** |
| `area` — не строка или отсутствует в `config.areas` со `status: "verified"` | Считается «район не выбран» (молча, `PRODUCT.md` 9.7: удалённая сущность игнорируется); значение в хранилище не стирается — район может вернуться в справочник |
| `start`/`end` не в формате `YYYY-MM-DD` или не существуют как дата | Считаются `null` |
| `start > end` | Обе даты считаются не заданными → состояние «Без дат» **[I3-5]** |
| `localStorage` недоступен (приватный режим) | Всё приложение работает как «первый запуск без сохранения»: выбор района действует **только до перезагрузки**, запись возвращает `false`, пользователь видит то же сообщение, что и в избранном (`place.js`) |

### 4.4 Запись

Одна функция записи целиком объекта (не по полям) — как `setPlaceSaved` **[I3-6]**: вызывающая сторона передаёт полный объект, `storage` его нормализует (лишние поля отбрасывает), сериализует и возвращает `true`/`false`. При `false` экран сообщает о неудаче и **не** делает вид, что сохранил.

### 4.5 Миграции

`SCHEMA_VERSION` остаётся `1`: новых полей у существующих ключей не появляется, `stg:trip` — новый ключ, старых данных для него нет. `ensureSchema()` не меняется.

## 5. `js/storage.js` — предлагаемый контракт

```js
// Возвращает { start, end, area, isFirstRun } — нормализованное значение,
// пригодное для прямого использования view. Никогда не бросает исключение.
function getTrip() {}

// Полная перезапись stg:trip. Возвращает true/false, как setPlaceSaved.
function setTrip({ start, end, area }) {}
```

- Обе функции добавляются в экспортируемый объект `storage`, порядок ключей не меняется.
- `getTrip()` **не** обращается к `config.json` — проверку `area` на существование делает view (у него уже загружен `config`) **[I3-7]**. Это сохраняет правило «`storage.js` знает только про хранилище».
- Комментарий `KEYS.trip` «зарезервировано, не используется в этой итерации» удаляется — он станет неверным.

## 7. Экран `#/settings` и первый запуск [пункты задания 1, 3, 4]

### 7.1 Одна форма для двух случаев

MVP-UX-SPEC §8 (решение №2) описывает первый запуск как **один экран** с двумя необязательными блоками и явно говорит, что позже те же данные меняются «в `#/settings`, та же форма». `PRODUCT.md` 8.2 описывает первый запуск как **два экрана** — это расхождение **[К3-1]**; следуем MVP-UX-SPEC как источнику истины по UX (его собственный раздел «Source of Truth»).

Отсюда: **один экран `#/settings`, два режима отображения** — первый запуск и обычные настройки **[I3-9]**. Отличие только в текстах и в наличии ссылки «Пропустить всё».

### 7.2 Блоки экрана

| # | Блок | Содержание | Требования |
|---|---|---|---|
| 1 | Заголовок | Первый запуск: приветствие + пояснение, что оба поля необязательны. Настройки: «Поездка» | Тексты — в коде (прецедент `PHASE_LABELS`) |
| 2 | «Когда поездка?» | Два поля даты (`<input type="date">`, нативный контрол — без библиотек, D-23/D-28); пустые значения допустимы | Шрифт ≥ 16px (иначе iOS зумит страницу — тот же приём, что в `copyText()` в `place.js`) |
| 3 | «Где вы живёте?» | Список районов из `config.areas` (только `verified`), в порядке файла, + вариант «Пока не выбрано» | Каждый вариант — цель ≥ 44×44 px; одиночный выбор (radio-группа с подписями) |
| 4 | Действия | «Готово» (`.btn--primary`). В режиме первого запуска — дополнительно ссылка «Пропустить всё» мельче | «Готово» — в нижней половине экрана (`PRODUCT.md` 8.9) |
| 5 | Сообщение о неудаче сохранения | `role="status"`, как `.place-actions__status` | Только при `setTrip() === false` |

Ялунвань в этом списке — обычный вариант `yalong` с подписью из `config.json`: **«Ялонг Бэй (Ялунвань)»**. Отдельной логики для него нет; названия и порядок меняются правкой `config.json`, а не кода (D-20).

### 7.3 Поведение

| Действие | Что происходит |
|---|---|
| Открытие `#/settings` | `loadConfig()` (кэш уже прогрет, если пользователь был на «Местах»); при ошибке — стандартное состояние ошибки с «Повторить» (контракт экрана, foundation §7.3) |
| «Готово» | `storage.setTrip(...)` → при `true` уход на Главную через `ctx.back("#/")`; при `false` — сообщение, экран остаётся |
| «Пропустить всё» (только первый запуск) | `setTrip({ start: null, end: null, area: null })` — ключ создаётся, экран первого запуска больше не показывается **[I3-1]** → `ctx.back("#/")` / `location.replace("#/")` |
| Ничего не выбрано и нажато «Готово» | То же, что «Пропустить всё» — пустая поездка валидна (MVP-UX-SPEC §12: «Нет дат — не ошибка») |
| Повторный вход в настройки | Поля заполнены текущими значениями `stg:trip` |

### 7.4 Как показывается первый запуск

`renderHome()` при `trip.isFirstRun === true` **не** рисует Главную, а делает `window.location.replace("#/settings")` **[I3-10]**.

- `replace`, а не переход: история не растёт, «Назад» не возвращает на пустую Главную (инвариант foundation §3.5).
- Проверка делается только на `#/` — прямая ссылка на `#/places` или `#/place/<id>` первый запуск **не** показывает: приложение обязано быть полностью пригодным без настройки (D-08, MVP-UX-SPEC §8).
- Если `localStorage` недоступен, `isFirstRun` был бы `true` всегда → редирект зациклился бы. Поэтому при недоступном хранилище первый запуск показывается **не более одного раза за сессию страницы** (модульный флаг в `home.js`) **[I3-11]**.

## 10. Поведение без района и район `other` [пункты задания 10, 11]

|---|---|---|

## 15. История, Back/Forward и меняющийся контекст [пункт задания 15]

Инварианты foundation §3.5 остаются в силе: код **никогда** не добавляет записи в историю, все редиректы — `location.replace`, внутренние «Назад» — `ctx.back(parentHash)`, query меняется только `history.replaceState(history.state, …)`.

| Сценарий | Ожидаемое поведение | Почему так работает |
|---|---|---|
| Главная → иконка настроек → системный «Назад» | Возврат на Главную, `history.length` не изменился | Переход по `<a href="#/settings">` создаёт одну запись; Back её снимает |
| `#/settings` → «Готово» | Главная, новая запись не создаётся | `ctx.back("#/")`: `history.state.from` = `#/` → `history.back()` |
| Прямая ссылка на `#/settings` → «Готово» | Главная через `location.replace("#/")` | В `ctx.back()` нет родителя в `from` — сработает ветка `replace` |
| Первый запуск: старт на `#/` → авто-`replace` на `#/settings` → «Пропустить всё» | Главная; «Назад» уводит из приложения, а не в петлю | Редирект сделан `replace` — записи `#/` в истории не остаётся |
| `#/places?f=beach` → настройки → сменить район → Back на список | Список перерисован: новый порядок и новые «~N км», фильтры `f=beach` сохранены, позиция прокрутки восстановлена | Возврат меняет hash → `hashchange` → полный ре-рендер, который читает `stg:trip` заново |
| Forward после этого | Снова `#/settings` с актуальными значениями формы | Экран читает `stg:trip` при каждом рендере |
| `#/place/<id>` открыта до смены района, возврат к ней через Back/Forward | Блок «~N км от вашего района» пересчитан | Тот же ре-рендер по `hashchange` |
| Тапы по чипам после смены района | История не растёт, сортировка сохраняется | `renderResults()` пересортировывает, `replaceState` не трогает `key`/`from` |

**Ключевое следствие [I3-23]:** механизма подписки на изменение `stg:trip` не нужно. Любой экран получает актуальный контекст, потому что любой переход между разными hash вызывает `hashchange` и полный ре-рендер, а внутри одного экрана район измениться не может (сменить его можно только уйдя на `#/settings`). Никакого стора, шины событий или `storage`-event-слушателя не вводим (`CLAUDE.md`: без лишних абстракций).

**Известное ограничение, которое нужно проверить, а не «починить» заранее:** восстановление прокрутки привязано к записи истории (foundation §6.4). Если порядок списка изменился из-за смены района, восстановленная позиция укажет на другие места. Ожидаемое поведение фиксируем в валидации (§19) и решаем по факту наблюдения — заранее усложнять роутер не нужно ([OQ3-8]).

## 19. Validation criteria [пункт задания 17]

**Среда:** Live Server (D-25), DevTools 320×568 и 375×667, реальный телефон по локальной сети; браузеры D-31.

**`stg:trip` и хранилище**
- [ ] До первого запуска ключа `stg:trip` нет; после «Пропустить всё» он есть и равен `{start:null,end:null,area:null}`.
- [ ] Выбор района сохраняется и переживает перезагрузку и закрытие вкладки.
- [ ] Повреждённое значение (`stg:trip = "{"`, `stg:trip = "[]"`) → приложение работает как «район не выбран», в консоли одна понятная ошибка, ключ не перезаписан молча.
- [ ] `area: "нет-такого"` и `area: "<draft-район>"` → ведут себя как «район не выбран», значение в хранилище сохраняется.
- [ ] `start > end` → состояние «Без дат».
- [ ] `localStorage` недоступен → сообщение о неудаче, экран настроек не делает вид, что сохранил; первый запуск не зацикливается.
- [ ] В хранилище по-прежнему только ключи `stg:schema`, `stg:checklist`, `stg:saved`, `stg:trip`; `stg:schema` остаётся `1`.

**Расстояние и сортировка**
- [ ] Контрольные значения §8.1 совпадают с тем, что показано в интерфейсе (обе таблицы полностью).
- [ ] Граничные форматы: 10,151 км → «~10 км»; 0,000 км → как решено по [OQ3-3] (*решено 2026-09-13: «менее 0,1 км», §26.8*); значение < 10 → один знак с запятой.
- [ ] При выбранном районе список отсортирован по возрастанию расстояния; при равенстве сохранён порядок файла.
- [ ] Сортировка сохраняется после каждого тапа по чипу и после Back с карточки.
- [ ] `sortByDistance` не мутирует вход (сниппет: сравнение `places.json` до и после).
- [ ] Расстояние в строке списка и в карточке одного и того же места совпадает.

**Район не выбран / `other`**
- [ ] Без района: «~N км» нигде нет, порядок = порядок `places.json`, на списке видна плашка со ссылкой на `#/settings`.
- [ ] Тап по плашке открывает настройки; после выбора района и возврата плашки нет, появились расстояния.
- [ ] `other`: расстояний нет, порядок файла, плашка-приглашение **не** показывается (показывается нейтральное пояснение, [OQ3-2]).
- [ ] Наньшань (`area: "other"`) получает расстояние, когда район проживания выбран.

**`#/settings` и первый запуск**
- [ ] Первый запуск показывается один раз; после «Готово» и после «Пропустить всё» не возвращается.
- [ ] Прямая ссылка на `#/places` при отсутствии `stg:trip` первый запуск не показывает.
- [ ] Форма настроек предзаполнена текущими значениями; Ялунвань виден в списке под подписью из `config.json`.
- [ ] Ошибка загрузки `config.json` → состояние ошибки с «Повторить»; повтор восстанавливает экран.
- [ ] Все интерактивные элементы экрана ≥ 44×44; поля даты ≥ 16px (iOS не зумит).

**Главная**
- [ ] Четыре состояния переключаются сменой дат; «После поездки» использует компонент «Без дат» с изменённой строкой.
- [ ] «До поездки: N дней» и «День N из M» совпадают с ручным расчётом на граничных датах (канун, первый день, последний день, следующий день).
- [ ] Район отображается в состояниях «До поездки» и «В поездке»; без района строка не ломается.
- [ ] Каждая кнопка-сценарий открывает «Места» с ожидаемыми фильтрами (таблица §14) и с ожидаемым числом «Найдено N».
- [ ] «Рядом с отелем» без района ведёт в `#/settings`.
- [ ] «Сохранено: N» совпадает с числом `verified`-мест в `stg:saved` и исчезает при пустом избранном.
- [ ] Прогресс подготовки на Главной совпадает с «Готово X из Y» на `#/prepare`.

**История**
- [ ] Все сценарии §15 воспроизводятся; `history.length` растёт только от действий пользователя.
- [ ] grep по `js/`: `location.hash =` и `history.pushState` по-прежнему отсутствуют.
- [ ] `#/settings/` , `#/settings/x`, `#/setting` → `replace("#/")` без исключений в консоли.
- [ ] После тапов по чипам `history.state` = `{key, from}`, `key` не меняется.

**Общее**
- [ ] Нет горизонтальной прокрутки на всех экранах при 320 и 375px, включая `#/settings` с самой длинной подписью района.
- [ ] В консоли нет ошибок, кроме смоделированных.
- [ ] Критерий итерации `PRODUCT.md` 11.2: «смена дат меняет главную; сортировка по расстоянию корректна» — выполнен и подтверждён контрольными значениями.

## 20. Regression requirements [пункт задания 18]

Итерация 2 закрывалась 247 автопроверками и попиксельным сравнением экранов. Итерация 3 должна доказать, что ничего из этого не сломано.

### 20.1 Foundation

- [ ] Таблица маршрутов, `parseHash`, `matchRoute` работают для всех прежних адресов; подсветка вкладок прежняя (для `#/settings` — «Сейчас», [I3-8]).

## 21. Сценарий «Приехал в Санью, живу в Ялунване» (особое требование)

### 21.1 Путь целиком

`Сейчас → выбор/проверка района → Ялунвань → Места → расстояния → карточка места`

| Шаг | Что видит пользователь | Что должно работать | Состояние на 2026-09-12 |
|---|---|---|---|
| 1 | Открывает приложение, попадает на «Сейчас» | Первый запуск: форма дат и района. Если поездка уже настроена — состояние «В поездке»: «День N из M · Ялонг Бэй (Ялунвань)» | **Нужно реализовать.** Сейчас `#/` — заглушка «Здесь появится ваш персональный экран» |
| 2 | Хочет проверить или задать район | Иконка настроек на Главной → `#/settings` | **Нужно реализовать.** Маршрута нет: `#/settings` сейчас не совпадает ни с одним шаблоном и роутер делает `replace("#/")` |
| 3 | Выбирает «Ялонг Бэй (Ялунвань)» | Список из `config.areas` (только `verified`), выбор сохраняется в `stg:trip.area = "yalong"` | **Частично готово:** данные есть — `yalong` с центром 18.210833, 109.654444, `status: "verified"`; `loadConfig()` их уже отдаёт. Нет экрана и нет записи в `stg:trip` |
| 4 | Нажимает «Готово» | Возврат на Главную, состояние обновлено | **Нужно реализовать** (`ctx.back("#/")` — механизм уже есть) |
| 5 | Идёт в «Места» (вкладка или сценарий «Рядом с отелем») | Список открывается, фильтры — из URL | **Готово.** Список, чипы, «Найдено N», переходы работают с Итерации 2 |
| 6 | Видит расстояния | У каждой строки «~N км»; порядок — от ближнего к дальнему: пляж Ялонг Бэй ~3,5 км → лесопарк ~4,9 км → Улучжичжоу ~10 км → … → Наньшань ~48 км | **Нужно реализовать:** `distance.js`, `sortByDistance`, вывод в строке. Сейчас порядок = порядок файла, расстояний нет |
| 7 | Фильтрует, например «Природа» | 3 места, отсортированные по расстоянию: лесопарк ~4,9 км, Улучжичжоу ~10 км, Лухуйтоу ~17 км | **Частично:** фильтрация готова, сортировка — нет |
| 8 | Открывает карточку места | Блок «~N км от вашего района» между параметрами и описанием | **Нужно реализовать** (в `place.js` на этом месте стоит комментарий-заглушка) |
| 9 | Нажимает «Показать таксисту» | Полноэкранный экран с 亚龙湾, адресом и русским названием | **Готово.** Изменений не требует |
| 10 | Возвращается назад | Back → карточка → список с теми же фильтрами и позицией | **Готово** (foundation §6) |

### 21.2 Что в этом сценарии уже поддержано текущим кодом

1. Роутинг, история, прокрутка, защита от гонки рендера — весь путь шагов 5–10 уже проверен 247 автопроверками Итерации 2.
2. Данные готовы полностью: район `yalong` с координатами центра, 10 мест с `location`, 2 места непосредственно в Ялунване (`yalong-bay-beach`, `yalong-tropical-forest-park`).
3. Фильтры в URL уже позволяют Главной делать ссылки-сценарии без единой строки нового состояния.
4. Экран таксиста, избранное, копирование — не затрагиваются.

### 21.3 Что нужно построить именно для этого сценария

| Нужно | Раздел плана |
|---|---|
| `#/settings` + `views/settings.js` + запись `stg:trip` | §6, §7 |
| `storage.getTrip()` / `setTrip()` | §5 |
| `logic/distance.js` + `sortByDistance` | §8, §9 |
| Расстояние и сортировка в списке | §11 |
| Блок расстояния в карточке | §12 |
| Состояния Главной и сценарии-ссылки | §13, §14 |

### 21.4 Что важно проверить именно на Ялунване

1. **Внутри «своего» района нули не появляются:** ближайшее место — 3,5 км (§8.1, наблюдение 2). Пользователь, живущий в Ялунване, увидит «~3,5 км» до пляжа, до которого может идти пешком. Это следствие того, что центр района взят по точке залива, а координата пляжа — по OSM. Фактам это не противоречит (расстояние по прямой между двумя разными точками), но при UX-проверке выглядит контринтуитивно — стоит показать владельцу вместе с [OQ-1].
2. **Граничный формат:** Улучжичжоу от Ялунваня — 10,151 км, ровно на переходе «один знак → целое» (ожидается «~10 км»).
3. **Разброс базы:** от 3,5 до 48 км. При 10 местах список «от ближнего к дальнему» осмыслен целиком; на базе 25–40 мест (D-05) хвост станет длиннее — это аргумент к проверке риска «0 результатов при 3+ фильтрах» (MVP-UX-SPEC §1.2 п. 2) уже на реальном объёме.
4. **Ялунвань и «В помещении»:** кнопка сценария даст 0 результатов (§14) — на этом сценарии ошибка заметнее всего, потому что пользователь в дождь окажется в пустом списке.

## 26. Фактический контракт после ревью модели проживания (реализовано 2026-09-12)

Раздел фиксирует **то, что фактически в коде** после выполнения слоёв C0 и C1 из
`ITERATION-3-LOCATION-REVIEW.md`. Он не отменяет разделы 1–25 (они описывают план и
остаются историей), но при расхождении верен этот раздел.

**Причина изменения:** QA на iPhone — в Ялунване пляж Ялунвань показывался как «~3,5 км».
Дефект не в координатах, а в модели: район использовался одновременно как логический
контекст и как географическая точка (ревью §1).

### 26.1 `stg:trip` — фактическая схема

```json
{ "start": "2026-11-12", "end": "2026-11-27", "area": "yalong",
  "stay": { "source": "spot", "spotId": "yalong-beach-front" } }
```

`stay` необязателен и равен `null`, если точка не задана. `source`: `"spot"` (хранится
только `spotId` — D-20/[I3-3]), `"manual"` / `"gps"` (хранится `point` WGS-84, у `gps`
дополнительно `updatedAt`; UI Итерации 3 их не создаёт, контракт готов к Итерации 5).
`SCHEMA_VERSION` остаётся `1`, миграция не нужна: старое значение без `stay` читается как
`stay: null` и даёт **побитово прежнее поведение**.

Защита при чтении (`normalizeStay()` в `js/storage.js`): не-объект, неизвестный `source`,
`spot` без `spotId`, координаты не-числа или вне диапазонов → `stay: null` + один
`console.error`; сырое значение в хранилище **не перезаписывается** ([I3-4]).
`spotId`, которого нет в справочнике, — не ошибка чтения: `resolveOrigin()` молча
откатывается на центр района (PRODUCT.md 9.7), значение сохраняется.

**Белый список полей в `setTrip()`** теперь включает `stay`. Вызывающая сторона обязана
передавать `stay` целиком — иначе поле теряется при сохранении (ревью §5.3).

### 26.2 `resolveOrigin(trip, config)` — единственное место с правилом приоритета

`js/logic/trip.js`, чистая функция → `{ point, precision, label }`:

| Приоритет | Условие | `precision` |
|---|---|---|
| 1–2 | `stay.source === "gps" \| "manual"` с валидной точкой | `"exact"` |
| 3 | `stay.source === "spot"`, `spotId` найден в `config.areas[].spots` выбранного района | `"exact"` |
| 4 | точки нет / не разрешилась, район выбран и имеет `center` | `"area"` |
| 5 | район не выбран / неизвестен / `center === null` (`other`) | `"none"` |

`js/logic/distance.js` не изменился ни на строку. `sortByDistance(places, point)` не
изменился: он всегда принимал точку, а не район.

### 26.3 `config.areas[].spots` — необязательный справочник ориентиров

### 26.8 Финализация (2026-09-13)

**Решения владельца:**

1. Текущий набор из 6 `spots` сохраняется как MVP; расширение до 15–25 точек в Итерацию 3 не входит.
2. Расстояние, округляющееся до 0,0 км, показывается как **«менее 0,1 км»**; расчёт и сортировка не меняются; остальные значения — в прежнем формате.
3. Утверждена модель: `trip.area` — логический контекст района; `trip.stay` — точка проживания и отсчёта; `resolveOrigin()` определяет фактическую точку; при отсутствии конкретной точки допускается запасной вариант `area.center` с пометкой «от центра района».

**Изменение кода — только `formatDistance()` в `js/logic/distance.js`:**

```js
const rounded = Math.round(km * 10) / 10;
if (rounded === 0) return "менее 0,1 км";            // новое
if (rounded < 10) return `~${rounded.toFixed(1).replace(".", ",")} км`;
return `~${Math.round(km)} км`;
```

Порог — то же округление до 0,1, что уже выбирало формат: всё, что раньше давало «~0,0 км» (км < 0,05), теперь «менее 0,1 км»; 0,05 км и больше — как прежде («~0,1 км»). `haversineKm()`, `sortByDistance()`, `resolveOrigin()`, `stay`, `spots`, экраны и тексты подписей не менялись: подписи собираются как `${formatDistance(km)} ${from}`, поэтому на карточке получается «менее 0,1 км от места проживания» / «менее 0,1 км от центра района» без правки `place.js`.

**Контрольные значения после изменения** (совпали в интерфейсе, `ITERATION-3-CLOSEOUT.md` §8):
