Iteration 8: маршруты `#/places` (Места, режим Food, Shopping внутри Places), «Рядом

## 5. P2 issues

1. **BUG** — `data/info.json`, запись `smoking` (id `smoking`), поля
   `sources[0].url` и `sources[1].url` — пустые строки `""`.
   - Затронутый компонент: `#/info/smoking` (`js/views/info.js:232-239`,
     `renderInfoDetail`) — код безусловно ставит `a.href = src.url` без проверки
     на пустую строку (подтверждено чтением кода в этом аудите):
     ```
     item.sources.forEach((src) => {
       const a = document.createElement("a");
       a.href = src.url;
       ...
     ```
     Для пустой строки это даёт `<a href="" target="_blank" rel="noopener noreferrer">`
     — клик открывает текущую страницу в новой вкладке вместо первоисточника.
   - Evidence: `data/info.json` — оба источника раздела «Курение» (строки
     201–202) имеют `"url": ""`; остальные 9 записей Справки — с непустыми `url`.
   - Воспроизводимость: 100% — открыть `#/info/smoking`, кликнуть по любому из
     двух источников.
   - Эффект на пользователя: видимая, кликабельная, но нефункциональная ссылка
     «Источник:» на единственной из 10 карточек Справки — не крашит приложение
     и не блокирует чтение самого правила, но ломает конкретную заявленную
     функцию (проверка первоисточника).
   - Классификация: пограничный случай между BUG и CONTENT GAP — техническая
     причина (отсутствие guard на пустой `url`) и содержательная (сами URL не
     найдены/не заполнены) совпадают; закрывается правкой данных без изменения
     кода **или** добавлением guard в `info.js`, любого из двух достаточно.
   - Рекомендация: до релиза либо найти и добавить реальные `url` для этих двух
     источников (регуляторные документы КНР/Хайнаня часто без стабильного
     постоянного URL — если подтверждённого URL нет, использовать вторичный
     источник со ссылкой), либо (шире) добавить в `info.js` условие, скрывающее
     ссылку `<a>` при пустом `url`, чтобы будущие записи без URL не давали ту же
     проблему молча.

## 8. QA limitations

- **Нет доступа к реальным устройствам**: iOS Safari, Chrome Android, Яндекс
  Браузер не тестировались — только headless Google Chrome 152 на Mac
  (эмуляция мобильных viewport через `Emulation.setDeviceMetricsOverride`).
  Специфичное для iOS Safari поведение (например, собственный диалог разрешения
  геолокации, safe-area на реальном notch/Dynamic Island, реальный
  `beforeinstallprompt`, который на iOS вообще не существует) не проверено на
  живом устройстве.
- **Геолокация симулирована через CDP** (`Emulation.setGeolocationOverride`,
  `Browser.grantPermissions`/`resetPermissions`), а не через реальный GPS/Wi-Fi
  позиционирование телефона. Состояния SUCCESS/EMPTY/DENIED воспроизведены
  достоверно; состояние TIMEOUT (код 3, «заняло слишком много времени») не
  удалось детерминированно спровоцировать в headless-окружении — код ошибки в
  `describeGeoError()` присутствует и синтаксически корректен, но отдельно от
  DENIED/POSITION_UNAVAILABLE вживую не воспроизведён.
- **Offline протестирован как «сервер убит»**, что ближе к реальному офлайну, чем
  эмуляция `Network.emulateNetworkConditions(offline)` (которая не всегда
  перехватывает трафик самого Service Worker, см. память сессии), но это всё ещё
  не полноценный airplane mode на телефоне с реальным Wi-Fi/LTE.
  «Install to Home Screen» → офлайн-запуск как standalone-приложение с реального
  домашнего экрана не проверялся (стандартный режим эмулировался через
  `navigator.standalone`/`display-mode`, не через фактическую установку).
- **Визуальный QA ограничен структурным** (переполнение, touch-target размеры,
  наличие/отсутствие DOM-узлов) — не оценивались тонкие вещи вроде контраста
  цвета, читаемости шрифта на солнце, визуальной иерархии.
- **`prompt()` из синтетического клика в headless Chrome отклоняется браузером**
  (нет настоящего user gesture) — полный сценарий «установить приложение через
  системный диалог Chrome» до конца не пройден, только до появления баннера
  установки.
- **Не проверено поведение при повреждённом/переполненном localStorage**
  (например, `QuotaExceededError`) вживую — код в `storage.js` содержит
  try/catch-обработку на этот случай, но реального переполнения хранилища не
  провоцировалось.
- Этот отчёт сводит три независимых прохода: (1) целостность данных (JSON,
  схема, verified/draft pipeline, ссылки category/tag/area), (2) построчный
  статический разбор `js/`, `css/`, `sw.js`, `index.html`, (3) живое тестирование
  в headless Chrome. Разделы §3–§7 объединяют их результаты; два независимых
  живых прогона в headless Chrome (в рамках прохода 2 и отдельно) пришли к
  одинаковым выводам по навигации, фильтрам, «Рядом со мной», Food-режиму и
  офлайну — совпадение результатов повышает уверенность в них, но оба прогона
  выполнялись в одном и том же окружении (см. пункты выше), поэтому не заменяют
  проверку на реальных устройствах.
