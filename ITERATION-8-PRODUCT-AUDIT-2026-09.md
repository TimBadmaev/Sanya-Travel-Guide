## 1. Executive summary

Продукт уже закрывает почти весь «справочный» слой и заметную часть «компаньона»: рекомендованный и
личный план по дням, добавление места/экскурсии в день, избранное, офлайн-поиск по названию на трёх
языках, быстрые фильтры и подборщик, «рядом со мной», сценарии «если дождь / вечер / с детьми»,
экран для таксиста, Amap-маршрут, офлайн-PWA.

Реальное ограничение сейчас — **продукт ничего не знает о деньгах поездки**. Владелец явно назвал
учёт расходов задачей поездки, а в коде нет ни модели, ни экрана, ни ключа хранилища. Это единственная
функция из списка, которой нет вовсе, и её отсутствие заставляет туриста держать второе приложение
(заметки/таблица) на всю поездку.

Второе ограничение — **поиск находит только по названию**: «пляж», «duty free», «UNIQLO», «Хайтан»
либо ничего не находят, либо находят случайно. Данные (категория, теги, район, summary) для этого уже
есть — нужна только логика.

Третье — **план дня не помогает, когда планы меняются**: на экране дня есть «Если не хочется»
(текст), но нет действия «заменить день на лёгкое / в помещении». Механика замены уже существует
(режим `addTo` + «Заменить текущий план») — её просто не видно с экрана дня.

Остальные пункты задания (open now, departure mode, offline-индикатор, planned-vs-actual) либо требуют
изменения схемы контента, либо дают меньше пользы, чем стоят сейчас, — они описаны как P1/P2 со
спецификацией.

### 2.3 План и `isSameAsRecommended()`

`logic/plan.js → isSameAsRecommended(myDay, recDay)` сравнивает `origin === "recommended"` и
`JSON.stringify` каждого поля из `DAY_FIELDS` (`type,title,summary,morning,afternoon,evening,placeIds,
excursionIds,tips,alt`). Любое изменение этих полей в `plan.json` снимает у пользователя отметку
«✓ в моём плане» для этого дня. **Вывод: `plan.json` в этой итерации не трогается.** Новые функции
не должны писать в `stg:myplan` ничего, кроме существующих операций `logic/myplan.js`.

- Места: 6 категорий, флаги `short/easy/indoor/free/saved/kids`, подборщик «время + интерес + нагрузка»,
  «Рядом со мной» (GPS, 20 км), расстояние от точки проживания, поиск по `name.ru/en/zh`.
- Карточка места: параметры, фото с атрибуцией, summary/why/tips/story, часы и цена (текстом),
  ♡ избранное, «Добавить в мой план», «Показать таксисту» (китайское название + `addressZh`),

- Офлайн: cache-first SW, явный PRECACHE, баннер обновления, версия в «Справке».

## 4. P0 / P1 / P2

### P0 — критично (реализуется в этой итерации)

#### P0-1. Расходы поездки

- **Зачем.** Деньги — ежедневная реальная задача поездки; сейчас туристу нужен второй инструмент.
- **Сценарий.** Поужинал → открыл приложение → «+ Расход» → ввёл 320, ¥ уже выбран, тап «Еда» →
  «Сохранить». Вечером смотрит «Сегодня: 1 240 ¥ ≈ 14 632 ₽».
- **UX.** Вложенные экраны под «Сейчас» (без новой вкладки): `#/expenses` (итоги + список),
  `#/expenses/add`, `#/expenses/<id>` (правка/удаление), `#/expenses/settings` (курс и бюджет).
  Вход — карточка «Расходы сегодня» на Главной в поездке, ссылка «Расходы поездки» в других
  состояниях, строка «Расходы за день» на экране дня плана.
- **Данные.** Новый ключ `stg:expenses` (исходная сумма и валюта, категория, дата, заметка,
  необязательная ссылка на пункт плана). Контентные JSON не меняются.
- **Schema.** Только пользовательская, отдельный ключ, версия внутри значения (`v: 1`).
- **Сложность.** Средняя: один logic-модуль, один view-модуль, правки storage/app/home/plan/sw/css.
- **Offline.** Полностью локально, сети не требует.
- **Риски.** Потеря данных при очистке хранилища браузером (iOS для неустановленного сайта) →
  кнопка «Скопировать отчёт» как ручной бэкап; повреждённое значение не затирается молча.

#### P0-2. Курс поездки (ручной, офлайн)

- **Зачем.** Итог в рублях — главный вопрос «сколько я потратил»; живой API запрещён (X-13, D-28).
- **UX.** «1 ¥ = __ ₽», «1 $ = __ ₽», «1 € = __ ₽»; пусто — курс не задан.
- **Правило.** Суммы хранятся в исходной валюте; рубли считаются при показе по текущему курсу поездки.
  Нет курса — рублёвый итог помечается «+ 500 ¥ без курса», ложной точности нет.
- **Риски.** Смена курса меняет рублёвые итоги всех расходов — это явно подписано под итогом.

#### P0-3. Бюджет поездки

- **UX.** Одно число в ₽ → «Потрачено ≈ … · Осталось ≈ …» + полоса прогресса. Если часть расходов
  без курса — «Осталось» помечается как неполное.
- **«Запланировано»** — не делаем в P0: в данных нет числовых плановых цен (см. P1-1).

#### P0-4. Поиск по смыслу, а не только по названию

- **Зачем.** «пляж», «duty free», «UNIQLO», «Хайтан», «рынок» — естественные запросы туриста.
- **UX.** То же поле; подсказка «Название, район или тип места».
- **Данные.** Уже есть: `category` → имя из `config.categories`, `tags` → имена из `config.tags`,
  `area` → имя района, `summary`. Для экскурсий — `summary`.
- **Schema.** Не меняется.
- **Риски.** Больше совпадений по summary; порядок по-прежнему по расстоянию.

#### P0-5. «Если планы меняются» на экране дня плана

- **Зачем.** Решение «устал / дождь / не хочу далеко» принимается в конкретном дне.
- **UX.** Блок на `#/plan/<date>` (сегодня и будущие дни): «🌧 Дождь или жара — в помещении»,
  «Устали — лёгкие и короткие рядом», «Готовые сценарии на дождь». Ссылки ведут в существующий режим
  выбора места для дня (`#/places?addTo=<date>&f=…`), где уже есть «Добавить к текущему плану /
  Заменить текущий план». Новой логики планировщика нет.
- **Риски.** Нулевые для данных: запись в `stg:myplan` делают только существующие операции.

### P1 — сильное улучшение (спецификация, не в этой итерации)

#### P1-1. Planned vs actual

- **Зачем.** «План ~350 ¥, факт 387 ¥» по выезду.
- **Что мешает.** `price` — `{type, note}` со свободным текстом; у 28/52 мест цена неизвестна;
  у экскурсий цены нет вовсе. Автоматический «план» = выдумка.
- **Следующий шаг.** Необязательное поле контента `costEstimate: { cny: [min, max], note, verifiedAt }`
  у экскурсий (выезд — естественная единица бюджета), валидатор + PRECACHE bump; в UI дня:
  «План ~300–400 ¥ · Факт 387 ¥». **Факт по дню** реализован уже сейчас (P0-1), так что остаётся
  только плановая половина.

#### P1-2. Departure mode

- **Место в продукте.** Не новый экран, а состояние «Сейчас» в последний день периода плана
  (`resolveToday().day === total`): блок «День вылета» — чекаут, «адрес аэропорта для таксиста»
  (нужна запись в `contacts`/`info` с `addressZh` 三亚凤凰国际机场 и источником), запас времени
  (факт из официального источника аэропорта), ссылка на `info/luggage-delivery` и `info/tax-refund`,
  «Итог расходов поездки».
- **Почему не сейчас.** Требует нового verified-контента об аэропорте (время прибытия, терминалы) —
  без исследования это выдумка.

#### P1-3. Избранное и для экскурсий

`stg:saved` хранит id мест; экскурсии сохранить нельзя. Отдельный ключ `stg:savedExcursions`,
чип «Сохранённые» в «Экскурсиях». Низкая стоимость, низкая частота.

#### P1-4. Экспорт/импорт пользовательских данных

Сейчас реализован текстовый «Скопировать отчёт» по расходам. Следующий шаг — JSON-экспорт
всех `stg:*` в буфер и импорт вставкой (без сервера).

## 5. Expenses — проектные решения

### 5.1 Модель (`stg:expenses`)

```json
{
  "v": 1,
  "items": [
    {
      "id": "exp-lx3k9a-4f2c",
      "date": "2026-11-18",
      "amount": 320,
      "currency": "CNY",
      "category": "food",
      "note": "Ужин",
      "link": { "kind": "excursion", "id": "wuzhizhou-island-trip" },
      "createdAt": "2026-11-18T12:41:07.000Z",
      "updatedAt": "2026-11-18T12:45:00.000Z"
    }
  ],
  "lastCurrency": "CNY"
}
```

- `amount` — исходная сумма, > 0, до 2 знаков; **никогда не пересчитывается**.
- `currency` — `CNY | RUB | USD | EUR`.
- `category` — `food, transport, excursions, shopping, hotel, connectivity, fees, health, prep, other`.
- `link` — необязательная ссылка на пункт «Моего плана» этой даты (`place`/`excursion`), вместо
  предложенного в задании `linkedPlanItemId`: у пунктов плана нет собственных id, есть только id места
  или экскурсии.
- Невалидные элементы при чтении отбрасываются; неразбираемое значение **не затирается**: перед первой
  записью его сырая копия сохраняется в `stg:expenses:backup`.

### 5.2 Курс и бюджет (`stg:budget`)

```json
{ "v": 1, "base": "RUB", "rates": { "CNY": 11.8, "USD": 82.5 }, "budget": 250000 }
```

- `rates[X]` = сколько рублей в 1 единице X. Нет ключа — курс не задан.
- Базовая валюта зафиксирована `RUB` (поле есть в схеме на будущее, UI его не меняет).
- Бюджет — одно число в рублях или отсутствует.

### 5.3 Итоги

- Итоги «Сегодня», «За поездку», «По категориям», «По дням» — сумма **по исходным валютам**
  плюс «≈ N ₽ по курсу поездки».
- Нет курса для части расходов → «≈ N ₽ + 500 ¥ без курса». Ни один расход не показывается в рублях
  по выдуманному курсу.
- Все расчёты — чистые функции `js/logic/expenses.js`, без DOM и хранилища (PRODUCT.md 10.3).

## 8. Риски, которые учитывает реализация

1. `plan.json` не меняется → отметки «✓ в моём плане» не слетают.
2. Новые ключи хранилища отдельные → старые версии приложения их просто не читают; `stg:schema` = 1.
3. Новые JS-файлы обязаны попасть в `PRECACHE`, иначе офлайн-запуск упадёт на импорте → проверка
   замыкания + bump `CACHE_VERSION`.
4. Главная в поездке: сценарии и карточка плана должны остаться на первом экране 320×568 — карточка
   расходов ставится после карточки плана.
