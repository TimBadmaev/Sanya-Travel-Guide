## 2. Расходы

### 2.1 Экраны и маршруты

Все — вложенные экраны «Сейчас» (подсвечена вкладка «Сейчас», как у `#/plan` и `#/settings`);
новой вкладки нет.

| Маршрут | Экран |
|---|---|
| `#/expenses` | итоги «Сегодня» / «Вся поездка», курс, бюджет, «По категориям», «По дням», «Скопировать отчёт» |
| `#/expenses/add` (`?date=ГГГГ-ММ-ДД`) | новый расход |
| `#/expenses/<exp-id>` | правка и удаление (с инлайн-подтверждением) |
| `#/expenses/settings` | курс ¥/$/€ → ₽ и бюджет |

Входы: карточка «Расходы сегодня» + кнопка «+ Расход» на «Сейчас» в поездке (после карточки плана —
первый экран 320×568 со сценариями и планом не сдвинут); ссылка «Расходы поездки» до поездки
(предпоездочные траты — категория «Подготовка») и после поездки (если есть записи); блок
«Расходы за день» на `#/plan/<date>`.

**Сценарий «несколько секунд»:** «+ Расход» → курсор уже в «Сумме» (где браузер разрешает фокус без
жеста) → валюта предвыбрана (последняя использованная, для первого расхода — ¥) → тап по категории →
«Сохранить». Дата — сегодня по умолчанию. Комментарий и привязка к плану — необязательны.
После сохранения — `history.back()` туда, откуда пришли, история не растёт.

### 2.2 Модель данных (`stg:expenses`)

```json
{
  "v": 1,
  "items": [
    { "id": "exp-mfx1k2-a9c3", "date": "2026-11-19", "amount": 320, "currency": "CNY",
      "category": "food", "note": "Ужин",
      "link": { "kind": "excursion", "id": "wuzhizhou-island-trip" },
      "createdAt": "2026-11-19T12:41:07.000Z", "updatedAt": "2026-11-19T12:45:00.000Z" }
  ],
  "lastCurrency": "CNY"
}
```

- Хранится **исходная сумма и исходная валюта**; при записи ничего не пересчитывается.
- Валюты: `CNY` ¥, `RUB` ₽, `USD` $, `EUR` €.
- Категории: `food` Еда, `transport` Транспорт, `excursions` Экскурсии, `shopping` Покупки,
  `hotel` Отель, `connectivity` Связь, `fees` Комиссии, `health` Здоровье, `prep` Подготовка, `other` Прочее.
- `link` вместо `linkedPlanItemId` из задания: у пунктов «Моего плана» нет собственных id — есть
  только id места или экскурсии. Варианты ссылки — пункты «Моего плана» на выбранную дату; поле
  скрыто, если в дне ничего нет.
- Сумма > 0, до 2 знаков, ≤ 100 000 000; ввод принимает «320», «320,50», «1 200».
- Итоги считаются в сотых долях целыми числами (0,1 + 0,2 = 0,3 ровно).

### 2.3 Курс и бюджет (`stg:budget`)

```json
{ "v": 1, "base": "RUB", "rates": { "CNY": 11.8, "USD": 82.5, "EUR": 90 }, "budget": 250000 }
```

- `rates[X]` — рублей за 1 единицу X, вводит пользователь («1 ¥ (юань) = … ₽»). Пустое поле — курс
  не задан. Приложение не содержит ни одного «актуального» курса.
- Базовая валюта — рубль; поле `base` есть в схеме на будущее, UI его не меняет.
- Смена курса меняет только рублёвые итоги; исходные суммы остаются. Экран это прямо пишет.

### 2.4 Итоги и честность пересчёта

| Ситуация | Что видит пользователь |
|---|---|
| все валюты с курсом | `320 ¥ + 1 500 ₽` и `≈ 5 276 ₽` |
| часть без курса | `≈ 1 500 ₽ + 320 ¥ без курса` + плашка «Не задан курс ¥ — итог в рублях неполный» |
| ни одного курса, не только рубли | «Итог в рублях не посчитан: не задан курс ¥» |
| только рубли | без строки «≈» |
| бюджет + часть без курса | «Потрачено ≈ … · Осталось ≈ …» и «Без учёта 320 ¥: не задан курс.» |
| перерасход | «Перерасход ≈ …», полоса красная |

«По категориям» — по убыванию рублёвого итога; «По дням» — новые даты сверху.

### 2.5 Хранилище и совместимость

- Новые ключи `stg:expenses`, `stg:budget`, `stg:expenses:backup`; `stg:schema` остаётся `1`
  (прецедент `stg:myplan`, `stg:installHintDismissed`). Версия — внутри значения (`v: 1`), чтобы
  будущая миграция могла отличить формат.
- Существующие ключи (`stg:trip`, `stg:checklist`, `stg:saved`, `stg:myplan`) не читаются и не
  пишутся новым кодом, кроме чтения `stg:myplan` для списка пунктов дня. Проверено сравнением сырых
  значений до и после операций с расходами.
- Повреждённое `stg:expenses` читается как пустое и **не перезаписывается при чтении**; перед первой
  записью поверх него сырая копия один раз сохраняется в `stg:expenses:backup` (последующие
  повреждения бэкап не затирают).
- Отдельные невалидные записи (неизвестная валюта/категория, несуществующая дата, сумма ≤ 0)
  отбрасываются при чтении. Ограничение: при следующей записи они исчезнут — такие записи может
  создать только ручная правка хранилища.
- «Скопировать отчёт» — текстовый ручной бэкап: iOS может очистить данные неустановленного сайта.

### 2.6 Planned vs actual

Реализована фактическая половина: «Расходы за день» на экране дня плана и привязка расхода к
пункту дня. Плановая половина — P1: в контенте нет числовых цен (у 28/52 мест `price.type = unknown`,
у экскурсий цены нет вовсе). Следующий шаг: необязательное поле `costEstimate: { cny: [min, max],
note, verifiedAt, sources }` у экскурсий, валидатор, PRECACHE bump; в дне — «План ~300–400 ¥ · Факт
387 ¥». «Запланировано» в бюджете появится тогда же, как сумма `costEstimate` пунктов будущих дней.

## 3. Поиск по смыслу

- `applySearch(items, query, fields, key, extraText)` — новый необязательный параметр `extraText`;
  без него поведение прежнее (так работает «Еда»).
- Места: название ru/en/zh **+** имя категории и `searchAliases` категории **+** имена тегов **+** имя
  района **+** `summary`. Текст собирается один раз на экран (`placeSearchText()`).
- Экскурсии: `title.ru/zh` + `summary`.
- Регистр и «ё» не важны.
- `config.json → categories[].searchAliases` — новое необязательное поле (контент, не код):
  «пляж, море», «парк, лес», «музей, храм», «шоу, аквапарк, аквариум», «рынок», «шопинг, магазин,
  ТЦ, аутлет, дьюти фри, mall, outlet, duty free». Потребитель — только `placeSearchText()`;
  `loadConfig()` копирует категории целиком.
- Подсказка поля: «Название, район или тип места» / «Название или что посмотреть».

Примеры (на текущих данных): «пляж» — 7 (все 4 пляжа + места, где пляж в описании), «шопинг» — все 14
shopping, «duty free» — CDF и duty-free комплексы, «хайтан» — всё в районе Хайтан, «UNIQLO», «大东海»,
«Yalong Bay», «С детьми» — по тегу.

## 4. «Если планы меняются» на экране дня плана

Блок на `#/plan/<date>` для сегодня и будущих дней (прошлый день не заменить):

| Ссылка | Правило | Куда |
|---|---|---|
| 🌧 Дождь или жара — места в помещении | `setting = indoor` | `#/places?f=indoor&addTo=<date>` |
| 😮‍💨 Устали — лёгкие места до 2 часов | `effort = low` И `durationHours[0] ≤ 2`, в радиусе 20 км от жилья, если точка известна | `#/places?f=easy,short&near=1&addTo=<date>` |
| 🧭 Готовые сценарии на дождь | тег `rain` у экскурсии | `#/excursions?f=rain` |

Режим `addTo` — существующий (Итерация 6): карточка места → «Добавить на <дату>» → «Добавить к
текущему плану» / **«Заменить текущий план»**. Никакой новой логики планировщика и никаких записей в
`stg:myplan`, кроме существующих операций `logic/myplan.js`. В полном дне (3 пункта) вместо ссылок —
«сначала очистите день».

## 7. Принятые допущения

1. Вкладок пять, а не четыре (как в задании) — сохранено, шестой нет.
2. Базовая валюта зафиксирована RUB (задание: «по умолчанию RUB»; смена базы — не нужна для этой поездки).
3. Категория расхода обязательна (без неё — подсказка), чтобы не записывать молча «Прочее».
4. Курс поездки один на всю поездку, а не на дату: проще и честно подписано.
5. `plan.json` не менялся — отметки «✓ в моём плане» сохраняются (проверено тестом).
6. Коммит не делался (явной convention на коммит в этом запуске нет); push — тем более.
