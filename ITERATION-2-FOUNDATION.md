## 1. Goal

Перед «Местами» привести к одному образцу четыре механизма. Без этого новые экраны скопируют их в нынешнем слабом виде:

1. **Роутинг:** одна таблица маршрутов с параметрами и поддержкой query в hash.
2. **Async-рендер:** единая защита от неактуального рендера на уровне роутера вместо копий в каждом экране.
3. **Кэш данных:** Promise-кэш в `data.js` — один запрос на файл, дедупликация параллельных вызовов, сброс при ошибке.
4. **Back / scroll / sticky:** прокручивается только документ; новый экран открывается сверху; Back восстанавливает позицию; внутренний «Назад» не увеличивает историю; `position: sticky` работает.

Плюс единый **контракт жизненного цикла экрана** — это договорённость, а не фреймворк.

**Критерий успеха.** После foundation «Подготовка» и «Справка» работают как раньше, за вычетом исправленных дефектов из 2.4. «Места» реализуются добавлением маршрутов и модулей экранов без правок инфраструктуры. Единственное исключение — флаг `fullscreen`, он добавляется вместе с экраном «Показать таксисту» (6.6).

Foundation не добавляет продуктовых функций, данных, контента и зависимостей. Правки C1–C8 визуально интерфейс не меняют (проверено, см. 2.4). C9 — отдельное исправление «Подготовки», оно требует решения владельца.

### 2.2 Текущий поток рендеринга

`hashchange` → `render()` → `getCurrentPath()`: вся строка после `#`, **включая** `?query` → `matchRoute()`: `routes[path]` (поиск по обычному объекту) или regex детали справки → неизвестный маршрут: `location.replace("#/")` → `updateActiveNav()` → `Promise.resolve(route.render(view)).catch(console.error)`.

Экраны пишут прямо в `#view`. Async-экраны сами разбирают `location.hash`, чтобы понять, актуальны ли они после `await`.

## 3. Routing

### 3.1 Решение

Заменить «объект точных маршрутов + отдельную ветку для `#/info/<id>`» **одной упорядоченной таблицей маршрутов** (массив) с якорными регулярными выражениями.

Почему:
- «Места» добавят два параметризованных маршрута: `#/place/<id>` и `#/place/<id>/taxi`. Отдельная ветка на каждый — это размножение нынешнего паттерна.
- Массив и якорные шаблоны убирают P2 без специальных проверок.

Библиотеки не нужны. Регулярки уже используются в проекте (`INFO_DETAIL_PATTERN`), а именованные группы поддерживаются нативно (Safari 11.1+).

### 3.2 Формат записи маршрута

```js
{ pattern: /^\/info\/(?<id>[^/]+)$/, render: renderInfoDetail, nav: "/info" }
```

- `pattern` — якорный (`^…$`) RegExp по **пути без query**. Параметры задаются именованными группами. `[^/]+` — ровно один сегмент, поэтому `/place/x/taxi` не совпадёт с шаблоном карточки.
- `render(container, ctx)` — функция экрана (контракт в разделе 7).
- `nav` — какая вкладка подсвечивается. У вложенных экранов — родительская.
- `fullscreen: true` — добавляется **только вместе с экраном таксиста** (6.6).
- Выигрывает первое совпадение. Все шаблоны якорные, поэтому порядок в массиве на результат не влияет.
- Параметры не декодируются: id по схеме — латиница и дефисы (`PRODUCT.md` 9.2). Существует ли запись с таким id, проверяет экран по данным, а не роутер.

### 3.3 Query

- `#/places?cat=beach` → путь `/places` матчится, а query передаётся экрану как `URLSearchParams` в `ctx.query`. Query — всё после первого `?` в hash.
- Имена и формат параметров определяет экран; это решение сеанса «Мест». Неизвестные параметры экран игнорирует.
- **Менять query изнутри экрана без навигации** (переключение фильтров) можно только так: `history.replaceState(history.state, "", newHash)`. Это:
  - не вызывает `hashchange`, поэтому экран не перерисовывается целиком — сохраняются прокрутка ряда чипов и фокус;
  - не создаёт запись истории, поэтому Back не проходит по каждому переключению чипа;
  - требует первым аргументом **именно `history.state`**, иначе теряются `key` и `from` записи, а с ними восстановление прокрутки и `ctx.back` (раздел 6).
- **Для фильтров запрещено:** `location.hash = …` (новая запись на каждый тап) и `location.replace(…)` (полная перерисовка).

**Рекомендация для «Мест»: фильтры хранятся в URL как единственный источник истины.**
- Back с карточки вернёт список с теми же фильтрами без дополнительного кода.
- Сценарии Главной (Итерация 3, `PRODUCT.md` 8.3: «список мест с заранее включёнными фильтрами») становятся обычными ссылками.
- Фильтры переживают перезагрузку.

Это не противоречит MVP-UX-SPEC §4 («порядок применения — в состоянии экрана, не в `localStorage`»): URL и есть состояние экрана, а порядок значений в параметре может кодировать порядок применения.

### 3.4 Неизвестные маршруты и невалидные параметры

- Путь не совпал ни с одним шаблоном → `location.replace("#/")`, как сейчас.
- Шаблон совпал, но записи с таким id нет или она не `verified` → экран вызывает `location.replace(<родитель>)`:
  - `#/info/<bad>` → `#/info` (как сейчас);
  - `#/place/<bad>` и `#/place/<bad>/taxi` → `#/places`.
- Экран делает это только после проверки `ctx.isCurrent()` (раздел 4).

### 3.5 Инварианты истории (защита от history loop)

1. **Код никогда не добавляет запись в историю.** Запрещены `location.hash = …` и `history.pushState`. Запись создаёт только пользователь — тапом по `<a href="#/…">`.
2. Все редиректы — `location.replace(…)`.
3. Внутренние «Назад» и «Закрыть» — только через `ctx.back(parentHash)` (6.5). Внутри это `history.back()` или `location.replace`, но никогда не push.
4. Query без навигации меняется только через `history.replaceState(history.state, "", …)`.

Следствия:
- Back никогда не ведёт на адрес, с которого код делает редирект.
- История не растёт от действий кода.

Проверка: grep по `js/` не находит `location.hash =` и `pushState`; сценарии раздела 13.

### 3.6 Совместимость

- Все текущие адреса (`#/`, `#/places`, `#/prepare`, `#/info`, `#/info/<id>`) и `href` в `index.html` не меняются.
- Правила подсветки вкладок те же.
- `home.js` и `places.js` не меняются: второй аргумент `ctx` они просто игнорируют.

## 4. Async rendering

### 4.1 Проблема

Нынешние `isPrepareRouteActive()` и `isInfoRouteActive()`:
- заново разбирают `location.hash` в каждом экране — вместе с `app.js` это три копии разбора;
- сравнивают **маршрут**, а не **навигацию**. Любой рендер под `/info*` считает себя актуальным — отсюда P3;
- несовместимы с query. Когда роутер начнёт принимать query (C1), `isPrepareRouteActive()` без C8 на `#/prepare?x` сравнит `"/prepare?x"` с `"/prepare"`. При незакэшированных данных экран навсегда останется в состоянии «Загрузка чек-листа…».

### 4.2 Решение: счётчик навигаций в роутере

- В `app.js`: `let navId = 0`. Каждая обработка маршрута начинается с `const id = ++navId`. Экран получает `ctx.isCurrent = () => id === navId`.
- **Правило для экранов:** после каждого `await` сразу `if (!ctx.isCurrent()) return;` — до любого изменения DOM и до редиректа.

Почему именно так:
- **Не сравнение строки hash.** `replaceState` для фильтров меняет hash без навигации, и сравнение строк ложно сочло бы экран устаревшим. Счётчик меняется только при реальной навигации.
- **Не `AbortController`.** Отмена fetch сломала бы общий кэш (раздел 5): загрузка нужна и другим экранам. Флага достаточно.
- **Не «роутер сам грузит данные»** (route loaders). Это мини-фреймворк, который меняет контракт всех экранов, а задача решается без него.

### 4.3 Что гарантируется

- Старый async-рендер не перерисует новый экран, в том числе `#/places` ↔ `#/place/<id>` на одном источнике данных.
- Прокрутка после рендера восстанавливается только для актуальной навигации (раздел 6).
- Параллельные обращения к одному файлу дают один fetch (раздел 5).
- «Повторить» вызывает тот же render с тем же `ctx`. Если пользователь ушёл, кнопки уже нет в DOM. Если остался, `ctx` по-прежнему актуален.

## 5. Data caching

### 5.1 Решение

- Кэш переносится в `data.js`: `Map<path, Promise>`.
- Один fetch на файл за сессию страницы.
- Параллельные вызовы получают **тот же** Promise.
- При ошибке запись удаляется: следующий вызов (и «Повторить») делает новый fetch.
- Публичный API `data.js` не меняется: `loadChecklist()`, `loadInfo()`.
- Фильтр `verified` остаётся в загрузчиках и срабатывает на каждый вызов. Каждый вызывающий получает **новый массив**, поэтому его можно сортировать без побочных эффектов.
- Объекты записей общие для всех экранов: **не мутировать**.

### 5.2 Почему до «Мест»

- `places.json` понадобится минимум трём экранам: список, карточка, «Показать таксисту». В Итерации 3 — ещё и Главной. `config.json` нужен списку, карточке и настройкам. Кэш в каждом модуле экрана означал бы повторные загрузки и дублирование данных.
- «Показать таксисту» должен работать в авиарежиме в текущей сессии (`PRODUCT.md` 11.2, MVP-UX-SPEC §5). С кэшем в `data.js` повторный вызов загрузчика не делает сетевых запросов.
- Частичные ошибки обрабатываются сами: в `Promise.all([loadPlaces(), loadConfig()])` удачный файл остаётся в кэше, а повтор догружает только упавший.

### 5.3 Чего не делаем

«Data framework» не создаём: без TTL, событийной инвалидации, подписок, нормализации и `Object.freeze`. Обновлённый контент виден после перезагрузки страницы, как и сейчас. `fetch(…, { cache: "no-cache" })` остаётся.

## 6. Back / scroll / sticky

### 6.1 Какой элемент прокручивается

**Решение: прокручивается только документ (`window`).** Фактически так уже есть (P7). Правка лишь убирает объявления, которые ни на что не влияют, но запирают sticky.

Изменения в `css/styles.css`:
- `#app`: `overflow-x: hidden` → **`overflow-x: clip`**.
  - `hidden` делает `#app` скролл-контейнером. По правилу CSS Overflow парное `visible` при этом вычисляется в `auto` (проверено: computed hidden/auto). Sticky-потомки привязываются к такому контейнеру и «застревают».
  - `clip` обрезает так же, но скролл-контейнер не создаёт (проверено: computed clip/visible, sticky работает).
  - Попутно `clip` исключает программный горизонтальный сдвиг (focus, `scrollIntoView`), который `hidden` допускает.
- `.app-main`: **удалить `overflow-y: auto`** — элемент никогда не прокручивался (P7).
- Совместимость: `overflow: clip` поддерживается в Safari/iOS 16+ и Chrome 90+. На более старых iOS объявление игнорируется: страховочной обрезки нет, но и ловушки для sticky тоже нет. Переполнения сейчас нет (2.4). Фолбэк `overflow-x: hidden` перед `clip` **сознательно не ставим**: он вернул бы ловушку sticky на старых iOS.

Альтернатива отклонена: сделать прокручиваемым `.app-main` (`#app { height: 100dvh }`). Это визуальное изменение — шапка стала бы неподвижной. В iOS Safari внутренний контейнер не сворачивает адресную строку, не реагирует на тап по статус-бару, и его прокрутку всё равно пришлось бы восстанавливать вручную.

### 6.2 Правила для sticky

- Sticky-элемент — **прямой потомок `#view`** или обёртки, охватывающей весь контент экрана: sticky двигается только в пределах своего родителя.
- Между sticky-элементом и документом нет предков с `overflow: hidden | auto | scroll`; `clip` допустим.
- Нижний sticky над панелью навигации: `bottom: calc(var(--nav-height) + env(safe-area-inset-bottom))`, собственный фон, `z-index` ниже `.bottom-nav` (10).
- Не `position: fixed` для кнопок карточки: fixed не занимает место в потоке и перекрывает конец контента, а sticky занимает.
- Вложенная прокрутка допустима только горизонтальная (ряд чипов, MVP-UX-SPEC §13). Такой контейнер не должен содержать или оборачивать sticky-элементы.

### 6.3 Правило прокрутки при навигации

| Событие | Поведение |
|---|---|
| Новая навигация: ссылка, вкладка, редирект, первая загрузка | Экран открывается **сверху** |
| Back / Forward, включая свайп-назад в iOS | Возвращается позиция, **с которой пользователь ушёл с этой записи истории** |
| Перезагрузка страницы | Сверху: позиции хранятся в памяти (осознанное упрощение) |
| Тап по уже активной вкладке | `hashchange` нет, ничего не происходит — как сейчас |
| Изменения внутри экрана (фильтры) | Роутер прокрутку не трогает |

### 6.4 Механизм

1. В `init()`: `history.scrollRestoration = "manual"`. Режим задаётся на запись и наследуется новыми записями. **Почему не `auto`:**
   - P8: в Chromium auto-восстановление срабатывает с задержкой и перебивает решения приложения; спецификация предписывает иной порядок; WebKit не проверен. С `manual` поведение одинаково во всех движках и целиком в руках роутера.
   - При `auto` к моменту `hashchange` браузер уже может изменить `scrollY`, и позицию покидаемого экрана не сохранить корректно.
2. Каждой записи истории присваивается `history.state = { key, from }`. Если при рендере `history.state` пуст (новая запись: ссылка, редирект, первая загрузка), вызывается `history.replaceState({ key, from }, "")`.
   - `from` — hash предыдущего адреса из `event.oldURL`. Проверено: учитывает и изменения через `replaceState`. При первой загрузке `from = null`.
   - `key` — `Date.now()` + `Math.random()`. **Не `crypto.randomUUID()`**: он недоступен вне secure context, а проверка с телефона идёт по `http://192.168.x.x`.
3. В начале обработки `hashchange` — `scrollPositions.set(currentKey, window.scrollY)`: позиция покидаемой записи. При `manual` браузер её ещё не менял.
4. Перед вызовом экрана — `window.scrollTo(0, 0)`.
5. Когда промис рендера выполнен, и только если `ctx.isCurrent()`, — `window.scrollTo(0, scrollPositions.get(key) || 0)`. У новой записи сохранённой позиции нет, поэтому прокрутка остаётся 0.

**Требование к экранам:** промис рендера выполняется только после финальной записи в DOM (async-функция, которая дожидается данных до отрисовки). Иначе прокрутка восстановится раньше, чем появится контент. При Back данные почти всегда уже в кэше (раздел 5), рендер завершается в микрозадачах до отрисовки кадра, и мигания нет.

**Сценарий list → detail → back целиком:**
1. Список (запись K1) → тап по карточке → новая запись K2 (`from` = адрес списка с его query). Позиция K1 сохранена, K2 открылась сверху.
2. Системный Back или внутренний «Назад» → запись K1 со своим query → список отрисован с теми же фильтрами → позиция K1 восстановлена.
3. Forward → K2 с её позицией.

### 6.5 Внутренние «Назад» / «Закрыть»

**Проблема (P6).** Ссылка на родителя добавляет запись. Для «Закрыть» на «Показать таксисту» это ловушка:
1. История: [список, карточка, таксист].
2. «Закрыть» как ссылка → [список, карточка, таксист, карточка].
3. Системный Back снова открывает таксиста.

Чередование «Закрыть» и Back зацикливается; выбраться можно только двумя Back подряд.

**Решение — единая функция роутера `ctx.back(parentHash)`:**
- **Предыдущая запись — родитель** (путь из `history.state.from` совпадает с путём `parentHash`, query не сравнивается) → `history.back()`. Возврат к той же записи — с её фильтрами и восстановленной прокруткой; история не растёт.
- **Иначе** (глубокая ссылка, перезагрузка, пришли не с родителя) → `location.replace(parentHash)`. Родитель открывается вместо текущего экрана; история не растёт, из приложения пользователь не уходит.
- Разметка остаётся ссылкой `<a href="#/info">` (семантика, доступность). Обработчик `click` вызывает `event.preventDefault()` и `ctx.back(…)`.

**Совместимость с INFO-IMPLEMENTATION §7** («ведёт конкретно на `#/info` (не просто `history.back()`)»). Пункт назначения по-прежнему всегда `#/info`. `history.back()` используется, только когда предыдущая запись и есть `#/info`. Требование сохраняется, меняется механизм — фиксирую это явно, а не молча.

**Системный Back** работает штатно по hash-истории. После внутреннего «Назад» он ведёт туда, откуда пользователь пришёл на родителя, а не обратно на деталь.

### 6.6 Полноэкранный «Показать таксисту» (делается в сеансе «Мест»)

- Маршрут: `{ pattern: /^\/place\/(?<id>[^/]+)\/taxi$/, render: …, nav: "/places", fullscreen: true }`.
- В `render()` роутера: `document.getElementById("app").classList.toggle("is-fullscreen", Boolean(match.route.fullscreen))`. Строка выполняется на **каждой** навигации, поэтому при уходе с экрана, в том числе системным Back, шапка и панель возвращаются автоматически.
- CSS: `#app.is-fullscreen .app-header, #app.is-fullscreen .bottom-nav { display: none; }`, у `.app-main` уменьшенный `padding-bottom` — без `--nav-height`, но с `env(safe-area-inset-bottom)`.
- «Закрыть» → `ctx.back("#/place/<id>")`.
- **В foundation не добавляется:** без потребителя это мёртвый код (`PRODUCT.md` 5.4).

### 7.3 Контракт экрана

```
export async function renderX(container, ctx)
  container — #view
  ctx — { params, query, isCurrent, back }

1. Синхронно — состояние загрузки (<p class="loading">…</p>).
2. Данные — только через data.js.
3. После каждого await — if (!ctx.isCurrent()) return;
4. Ошибка загрузки — если экран актуален: .error-state + «Повторить» → renderX(container, ctx).
5. Нет записи по ctx.params.id — location.replace(<родитель>); return;
6. Пусто — .empty-state с подсказкой следующего действия (MVP-UX-SPEC §12).
```

**Экранам запрещено:**
- читать или разбирать `location.hash` — только `ctx.params` / `ctx.query`;
- переходить из кода с добавлением записи в историю (3.5);
- хранить загруженные **данные** в модуле. UI-состояние в модуле допустимо: `openPhases`, фильтры, если они не в URL;
- мутировать записи, полученные из `data.js`;

Синхронных заглушек контракт не касается.

### Эталонная реализация C1–C4 (`js/app.js`)

```js
import { renderHome } from "./views/home.js";
import { renderPlaces } from "./views/places.js";
import { renderPrepare } from "./views/prepare.js";
import { renderInfo, renderInfoDetail } from "./views/info.js";

// Первое совпадение побеждает; nav — подсвечиваемая вкладка.
const routes = [
  { pattern: /^\/$/, render: renderHome, nav: "/" },
  { pattern: /^\/places$/, render: renderPlaces, nav: "/places" },
  { pattern: /^\/prepare$/, render: renderPrepare, nav: "/prepare" },
  { pattern: /^\/info$/, render: renderInfo, nav: "/info" },
  { pattern: /^\/info\/(?<id>[^/]+)$/, render: renderInfoDetail, nav: "/info" },
];

let navId = 0;
let currentKey = null;
const scrollPositions = new Map();

function parseHash(hash) {
  const raw = hash.startsWith("#") ? hash.slice(1) : hash;
  const q = raw.indexOf("?");
  return {
    path: (q === -1 ? raw : raw.slice(0, q)) || "/",
    query: new URLSearchParams(q === -1 ? "" : raw.slice(q + 1)),
  };
}

function matchRoute(path) {
  for (const route of routes) {
    const m = path.match(route.pattern);
    if (m) return { route, params: { ...m.groups } };
  }
  return null;
}

// Внутренний «Назад»: всегда к родителю и никогда не добавляет запись в историю.
function back(parentHash) {
  const from = history.state && history.state.from;
  if (from && parseHash(from).path === parseHash(parentHash).path) {
    history.back();
  } else {
    window.location.replace(parentHash);
  }
}

function updateActiveNav(navPath) { /* без изменений */ }

function render(event) {
  const id = ++navId;
  if (currentKey) scrollPositions.set(currentKey, window.scrollY);

  const { path, query } = parseHash(window.location.hash || "#/");
  const match = matchRoute(path);
  if (!match) {
    window.location.replace("#/");
    return;
  }

  if (!history.state || !history.state.key) {
    const from = event && event.oldURL ? new URL(event.oldURL).hash : null;
    history.replaceState({ key: `${Date.now()}-${Math.random()}`, from }, "");
  }
  const key = history.state.key;
  currentKey = key;

  const ctx = { params: match.params, query, isCurrent: () => id === navId, back };
  updateActiveNav(match.route.nav);
  window.scrollTo(0, 0);

  Promise.resolve(match.route.render(document.getElementById("view"), ctx))
    .then(() => {
      if (ctx.isCurrent()) window.scrollTo(0, scrollPositions.get(key) || 0);
    })
    .catch((e) => {
      console.error("Ошибка рендеринга экрана", e);
    });
}

window.addEventListener("hashchange", render);

function init() {
  history.scrollRestoration = "manual";
  if (!window.location.hash) {
    window.location.replace("#/");
  } else {
    render(null);
  }
}
```

```js
const cache = new Map();

async function fetchJSON(path) {
  // тело нынешней loadJSON — без изменений
}

// Один запрос на файл за сессию страницы; при ошибке запись удаляется,
// чтобы «Повторить» сделал новый запрос.
function loadJSON(path) {
  if (!cache.has(path)) {
    cache.set(path, fetchJSON(path).catch((error) => {
      cache.delete(path);
      throw error;
    }));
  }
  return cache.get(path);
}
```
