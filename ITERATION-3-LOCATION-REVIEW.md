### 1. Проблема текущей модели

#### 1.1 Что реализовано сейчас

Модель зафиксирована в `PRODUCT.md` D-11 («расстояние от **выбранного района проживания**»)
и реализована буквально:

```js
// js/views/places.js, js/views/place.js — один и тот же код
const trip = storage.getTrip();                                        // { start, end, area }
const selectedArea = config.areas.find((a) => a.id === trip.area) || null;
const center = (selectedArea && selectedArea.center) || null;          // ЕДИНСТВЕННАЯ точка отсчёта
formatDistance(haversineKm(center, place.location));
sortByDistance(applyFilters(places, tokens, { savedIds }), center);
```

То есть: **район = точка**. `stg:trip.area` хранит только `id` ([I3-3]), а координата берётся
из `config.areas[].center`. Других источников точки в приложении нет.

#### 1.2 Почему на реальном сценарии это даёт неверное число

Тестовый сценарий: `Sanya Yalong Bay Swiss And Mercury Hotel`, 12–27 ноября, район `yalong`.

`config.json` → `yalong.center = { 18.210833, 109.654444 }`. Источник этой координаты —
[Wikidata Q8047513](https://www.wikidata.org/wiki/Q8047513), проверено 2026-09-11
(`CONTENT-PLACES.md` §2). Это **центроид залива**, точка в воде/на оси бухты, а не точка
отельной полосы.

Координата пляжа в `places.json` — `{ 18.224358, 109.624165 }`, источник OpenStreetMap,
`verifiedAt: 2026-09-11`. Между этими двумя точками — 3,534 км, отсюда «~3,5 км».

**Обе координаты корректны и подтверждены. Неверна не координата, а модель:**
приложение выдаёт расстояние между двумя условными точками района и подписывает его
«от вашего района» (`place.js`), а пользователь читает это как «от моего отеля».

#### 1.3 Это не единичный дефект данных, а свойство модели

| Наблюдение | Подтверждение |
|---|---|
| Район — протяжённый объект. Санья Бэй растянута на ~20 км вдоль берега; «центр» бухты — условность, а не единственно верная точка | `CONTENT-PLACES.md` §2 прим. 3 |
| По самому Ялунваню источники расходятся на ~2 км: Wikidata даёт 18.2108/109.6544, OSM — узлы посёлка в диапазоне 18.222–18.224 / 109.624–109.634. Выбран Wikidata | `CONTENT-PLACES.md` §2 прим. 3 |
| Внутри «своего» района ноль не получается — это было предсказано до QA | `ITERATION-3-IMPLEMENTATION.md` §8.1 набл. 2, §22 набл. 1 |
| Обратный перекос: `dadonghai-beach` имеет ровно координату центра `dadonghai` → «~0,0 км» | `ITERATION-3-IMPLEMENTATION.md` §8.1 набл. 1, [OQ-17] |
| От центра `city` до Первого рынка — 1,465 км, хотя рынок и есть исторический центр | `CONTENT-PLACES.md` §7 п. 3, [OQ-1] |
| Тяньяхайцзяо в `sanya-bay` физически далеко от точки центра этого района | `CONTENT-PLACES.md` §7 п. 2 |

То есть в текущей модели ошибка «центр района ↔ фактическое проживание» составляет
**от 0 до ~3–5 км в пределах одного района** и не ограничена сверху для крупных бухт.
Для дальних мест (Наньшань ~48 км) это безразлично, для ближних (свой пляж, свой лесопарк)
— это и есть всё число целиком.

#### 1.4 Что именно ломается для пользователя

| Симптом | Механика |
|---|---|
| «Мой пляж в 3,5 км» при отеле в 5 минутах ходьбы | §1.2 |
| Порядок списка тоже может быть неверным | От центроида: Улучжичжоу (10,2 км) выше Дадунхая (14,5 км). От точки отельной полосы: Дадунхай (11,3 км) выше Улучжичжоу (11,8 км) — **порядок меняется** |
| Подпись обещает больше, чем есть | `place.js`: «~3,5 км **от вашего района**» — формулировка не предупреждает, что точка условная |
| Сценарий «Рядом с отелем» на Главной ведёт в список, отсортированный **не от отеля** | `home.js`, [I3-18] |
| Для `other` расстояний нет вовсе, хотя пользователь район указал | `center: null` → [I3-15] |

#### 1.5 Что в текущей модели правильно и должно сохраниться

- `stg:trip` хранит **id**, а не дублирует справочные данные (D-20, [I3-3]).
- `distance.js` — чистый модуль: гаверсинус + формат, ничего не знает про trip/config/DOM.
- `sortByDistance(places, point)` принимает **точку**, а не район: подмена источника точки
  её не касается.
- Нет подписок на изменение `stg:trip`: любой переход даёт `hashchange` и полный ре-рендер ([I3-23]).
- Деградация «нет точки → нет расстояний, порядок файла» уже реализована и протестирована.

**Вывод раздела:** менять нужно **одно звено** — способ получения точки отсчёта. Формула,
сортировка, хранение id, роутинг и деградация остаются как есть.

### 3. Варианты

Общее для всех вариантов — **точка отсчёта перестаёт быть синонимом района**. Различаются
варианты только тем, **откуда берётся точка**.

#### 3.1 Вариант A — район + точка проживания из справочника

Идея: в `config.json` появляется справочник мест проживания (отели/ЖК/апартаменты)
с проверенными координатами; `stg:trip` хранит его `id`.

```json
{ "start": "2026-11-12", "end": "2026-11-27", "area": "yalong", "stayId": "swiss-mercury-yalong" }
```

| Критерий | Оценка |
|---|---|
| **UX** | Двухшаговый выбор: район → список отелей района. Поиск по названию нужен уже при 20+ записях (а это новый UI-компонент, которого в MVP нет). Для пользователя, чьего отеля нет в списке, экран выглядит как «приложение меня не знает» |
| **`stg:trip`** | `+ stayId: string \| null`. Красиво ложится на D-20/[I3-3]: в хранилище только id |
| **Первый запуск** | Блоков становится три (даты, район, жильё) или район+жильё сливаются в один каскад. MVP-UX-SPEC §8 «два необязательных блока» нарушается |
| **`#/settings`** | Каскадная зависимость: список отелей зависит от выбранного района, при смене района список надо перерисовывать и сбрасывать выбор. Это первый в проекте зависимый контрол |
| **Смена района** | `stayId` обязан сбрасываться (отель принадлежит району) |
| **Расчёт расстояния** | `origin = stays.find(s => s.id === trip.stayId)?.point ?? area.center ?? null` |
| **`other`** | Для `other` справочник жилья бессмыслен («за пределами центральных районов») → расстояний по-прежнему нет |
| **Нет точной точки** | Отель не из списка → откат к `area.center` → **исходная проблема возвращается в полном объёме** |
| **`config.json`** | Да: новый раздел `stays` (или отдельный `data/stays.json`). Каждая запись требует источника и даты (R7) |
| **`places.json`** | Нет |
| **`distance.js`** | Нет изменений |
| **`places.js`** | 2 строки: вычисление `origin` вместо `center` |
| **`home.js`** | 1–2 строки: «Рядом с отелем» становится осмысленным только при заполненном `stayId` |
| **Back/Forward** | Без изменений: состояние в `localStorage`, экраны читают его при каждом рендере |
| **reload** | Без изменений |
| **localStorage** | +1 поле, объём ничтожен |
| **GPS в Итерации 5** | **Плохо.** GPS даёт координату, а не id из справочника. Придётся вводить второе поле `point` — то есть всё равно приходить к варианту B/C, ломая уже выпущенный контракт |
| **Сложность реализации** | Код — низкая. **Контент — неограниченная**: в Санье сотни отелей и тысяч апартаментов; каждый нужно проверить по источнику (R7) и поддерживать. Это выход за рамки MVP (D-05: даже мест пока 10 вместо 25–40) |

**Главный дефект A:** он решает проблему только для тех, кто попал в справочник, и создаёт
контент-обязательство, которое проект не может выполнить. Проверить это легко на нашем же
сценарии: `Sanya Yalong Bay Swiss And Mercury Hotel` — конкретный отель, координат которого
в проекте нет и добыть их «правильно» (с источником и датой) для каждого отеля Саньи
невозможно.

#### 3.2 Вариант B — район + пользовательская точка с координатами

Идея: пользователь сам вводит координаты своего жилья.

```json
{ "start": "…", "end": "…", "area": "yalong",
  "stay": { "point": { "lat": 18.2243, "lng": 109.6239 }, "label": "Отель" } }
```

| Критерий | Оценка |
|---|---|
| **UX** | Самое слабое место. Турист не знает своих координат. Реальный путь — скопировать из карты, но: Google Maps в материковом Китае заблокирован (F-04), а Amap отдаёт **GCJ-02**, смещённые относительно WGS-84 (R-05, глоссарий `PRODUCT.md`). Пользователь вставит смещённую точку и не узнает об этом. Вводить два числа на телефоне под солнцем — антипаттерн для нашего контекста (8.9) |
| **`stg:trip`** | `+ stay: { point: { lat, lng }, label? } \| null`. Здесь хранение координаты оправдано: справочника, откуда её взять, не существует |
| **Первый запуск** | Поле координат в приветственном экране недопустимо — это отпугивающий шаг. Значит, только в `#/settings` как «дополнительно» → два разных состава формы, чего [I3-9] специально избегал |
| **`#/settings`** | +2 числовых поля (или одно поле «вставьте координаты» с разбором `18.2243, 109.6239`), + валидация диапазонов, + сообщение об ошибке. Это заметно больше кода, чем весь текущий `settings.js`-блок района |
| **Смена района** | Формально независимы; практически при смене района точка почти наверняка устарела → нужен вопрос пользователю или молчаливый сброс. Оба варианта неприятны |
| **Расчёт расстояния** | `origin = trip.stay?.point ?? area.center ?? null` |
| **`other`** | **Плюс варианта:** для `other` расстояния впервые становятся возможны — точка есть, центр района не нужен. Снимает тупик [I3-15] |
| **Нет точной точки** | Откат к `area.center`; поведение сегодняшнее |
| **`config.json`** | Нет изменений |
| **`places.json`** | Нет |
| **`distance.js`** | Нет изменений |
| **`places.js`** | 2 строки |
| **`home.js`** | 1–2 строки |
| **Back/Forward**, **reload**, **localStorage** | Без изменений |
| **GPS в Итерации 5** | **Отлично.** GPS пишет ровно в это поле; UI ввода становится запасным путём. Контракт не меняется |
| **Сложность реализации** | Код — средняя (валидация + разбор строки + тексты ошибок). UX-риск — высокий. Контент — нулевой |

**Главный дефект B:** правильная модель данных с почти непригодным для MVP способом ввода.

#### 3.3 Вариант C — «точка отсчёта» как разрешаемое значение (рекомендуется)

Идея: разделить **модель** и **способ заполнения**. В `stg:trip` появляется одно
необязательное поле `stay` с явным указанием **источника** точки; приложение нигде не
обращается к `area.center` напрямую, а вызывает одну чистую функцию-резолвер.

```json
{ "start": "2026-11-12", "end": "2026-11-27", "area": "yalong",
  "stay": { "source": "spot", "spotId": "yalong-hotel-strip" } }
```

```js
// js/logic/trip.js — чистая функция, без DOM/storage/location
// Возвращает { point, precision, label }:
//   precision: "exact" — точка проживания известна
//              "area"  — точка не задана, используется центр района (условная)
//              "none"  — точки нет вообще (нет района или у района нет центра)
export function resolveOrigin(trip, config) {}
```

Приоритет источников — единственное место в приложении, где это правило записано:

| Приоритет | `stay.source` | Точка берётся из | Появляется в |
|---|---|---|---|
| 1 | `"gps"` | `stay.point` (записан геолокацией) | Итерация 5 |
| 2 | `"manual"` | `stay.point` (ввёл пользователь) | Итерация 5 или позже, по потребности |
| 3 | `"spot"` | `config.areas[].spots[]` по `stay.spotId` (id, не координата — D-20) | Итерация 3.2 |
| 4 | — | `config.areas[].center` → `precision: "area"` | уже есть |
| 5 | — | `null` → `precision: "none"` | уже есть |

Заполнение в Итерации 3 — **самое дешёвое из возможных**: в `config.json` у каждого района
появляется короткий список проверенных **ориентиров** (`spots`), а не отелей:

```json
{ "id": "yalong", "name": "Ялонг Бэй (Ялунвань)",
  "center": { "lat": 18.210833, "lng": 109.654444 },
  "spots": [
    { "id": "yalong-hotel-strip", "name": "Отельная полоса у пляжа", "point": { "lat": 0, "lng": 0 },
      "source": "НУЖНО ПРОВЕРИТЬ", "verifiedAt": "НУЖНО ПРОВЕРИТЬ" }
  ],
  "status": "verified" }
```

3–5 ориентиров на район × 5 районов ≈ 15–25 проверяемых точек — конечный, выполнимый объём
контента (сравнить: сотни отелей в варианте A).

| Критерий | Оценка |
|---|---|
| **UX** | Один необязательный вопрос **после** выбора района: «Где именно?» — радиогруппа из 3–5 ориентиров + «Не знаю / где-то в районе». Ровно тот же контрол, что уже используется для района (radio, ≥44 px). Ничего не вводится руками |
| **`stg:trip`** | `+ stay` (раздел 5). Для `"spot"` хранится только id — D-20/[I3-3] соблюдён; координата хранится только там, где справочника нет (`gps`/`manual`) |
| **Первый запуск** | Блоков остаётся два. «Где именно?» — часть блока «Где вы живёте?», появляется под выбранным районом. MVP-UX-SPEC §8 не нарушается |
| **`#/settings`** | Та же форма (одна, [I3-9]). Зависимость от района — локальная перерисовка одного списка, без навигации |
| **Смена района** | `stay` сбрасывается в `null` (точка принадлежала прежнему району). Одна строка, предсказуемо. Альтернатива для `gps`/`manual` — в разделе 13 |
| **Расчёт расстояния** | Один вызов `resolveOrigin(trip, config)` во всех трёх экранах; `distance.js` и `sortByDistance` не меняются |
| **`other`** | Сегодня — как сейчас (у `other` нет ни центра, ни ориентиров → `precision: "none"`). С появлением `gps`/`manual` в Итерации 5 `other` автоматически получает расстояния — **без изменения контракта**. Тупик [I3-15] перестаёт быть постоянным |
| **Нет точной точки** | `precision: "area"` — всё работает как сегодня, но подпись честная: «от центра района». Никакой регрессии |
| **`config.json`** | Да: необязательное поле `spots` у районов. Существующие поля не трогаются, старый файл остаётся валидным |
| **`places.json`** | **Нет.** Ни одного изменения |
| **`distance.js`** | **Нет изменений.** Модуль остаётся чистой геометрией |
| **`places.js`** | 2 строки (`origin` вместо `center`) + текст плашки зависит от `precision` |
| **`home.js`** | 1–2 строки: «Рядом с отелем» ведёт в список при `precision !== "none"`; подпись района не меняется |

| Риск GCJ-02 (R-05) | Нет | Высокий | Нет (в Итерации 3) |
| `other` получает расстояния | Нет | Да | Позже, без смены контракта |
| Готовность к GPS | Требует ломки контракта | Готов | Готов |
| Регрессия к текущему поведению при пустом значении | Да | Да | Да |
| Объём кода | ~средний | ~больший | ~наименьший |

### 4. Рекомендованный вариант

**Вариант C.** Точка отсчёта — самостоятельное необязательное значение `stay` в `stg:trip`
с явным источником; все экраны получают её через одну чистую функцию `resolveOrigin()`;
в Итерации 3 значение заполняется выбором ориентира из короткого проверенного списка,
в Итерации 5 — геолокацией, без изменения контракта.

Внедрять **слоями**, каждый слой самостоятелен и может быть выпущен отдельно:

| Слой | Что | Даёт | Риск |
|---|---|---|---|
| **C0 (контракт)** | `stay` в `stg:trip` + `resolveOrigin()` + честные подписи по `precision` | Устраняет ложное обещание «от вашего района»; готовит место под точку | Практически нулевой: при `stay === null` поведение сегодняшнее |
| **C1 (заполнение)** | `spots` в `config.json` + блок «Где именно?» в `#/settings` | **Чинит реальный сценарий с Ялунванем** | Низкий; требует контент-прохода на 15–25 точек |
| **C2 (Итерация 5)** | GPS пишет `stay.source = "gps"` | Точность без ручного труда | Вне этой итерации |

Почему не A: неограниченное контент-обязательство и тупик по GPS.
Почему не B как основной путь: способ ввода непригоден для нашего пользователя (F-04, R-05),
хотя сама модель данных правильна — поэтому B сохранён внутри C как `source: "manual"`.

### 5. Изменение `stg:trip`

#### 5.1 Формат

```json
{
  "start": "2026-11-12",
  "end": "2026-11-27",
  "area": "yalong",
  "stay": { "source": "spot", "spotId": "yalong-hotel-strip" }
}
```

| Поле | Тип | «Не задано» | Комментарий |
|---|---|---|---|
| `start`, `end` | `YYYY-MM-DD` | `null` | Без изменений |
| `area` | `id` из `config.areas` | `null` | Без изменений. Остаётся логическим контекстом (R1) |
| `stay` | объект или `null` | `null` | **Новое.** Точка проживания |
| `stay.source` | `"spot" \| "manual" \| "gps"` | — | Обязателен, если `stay !== null` |
| `stay.spotId` | `id` из `config.areas[].spots` | — | Только при `source: "spot"` |
| `stay.point` | `{ lat, lng }` WGS-84 | — | Только при `source: "manual"` / `"gps"` (D-19) |
| `stay.updatedAt` | `YYYY-MM-DD` | отсутствует | Только для `gps` — чтобы Итерация 5 могла считать точку устаревшей |

**Правило D-20 сохранено:** координата хранится в `stg:trip` **только** когда справочника,
из которого её можно восстановить, не существует. Для `spot` хранится id ([I3-3]).

#### 5.2 Чтение (`storage.getTrip`)

Продолжает образец `getSavedIds()` / текущего `getTrip()`: повреждённое значение не ломает экран.

| Ситуация | Поведение |
|---|---|
| `stay` отсутствует (старое значение) | `stay: null` → поведение сегодняшнее. Ключ не перезаписывается ([I3-4]) |
| `stay` не объект / неизвестный `source` | `stay: null`, `console.error`, ключ не трогаем |
| `source: "spot"`, но `spotId` отсутствует в `config` | Молча «точки нет» → `precision: "area"` (`PRODUCT.md` 9.7: удалённая сущность игнорируется). Значение в хранилище **не** стирается — ориентир может вернуться в справочник |
| `source: "manual"/"gps"`, `point` не число или вне диапазонов (`lat` −90…90, `lng` −180…180) | `stay: null` + `console.error` |
| `localStorage` недоступен | Как сегодня: всё живёт до перезагрузки |

#### 5.3 Запись (`storage.setTrip`) — важная деталь реализации

Текущий `setTrip()` собирает **новый объект из белого списка полей**:

```js
const value = { start: …, end: …, area: … };   // js/storage.js
```

Значит, при добавлении `stay` **обязательно**:

1. добавить нормализацию `stay` в `setTrip()` — иначе поле будет молча теряться при каждом
   сохранении;
2. поправить `js/views/settings.js`, где форма вызывает
   `save({ start, end, area })` — иначе сохранение дат затрёт точку проживания.

Это единственные два места, где легко получить скрытую потерю данных. В план проверки
(раздел 14) они вынесены отдельными пунктами.

### 7. Изменение расчёта расстояния

#### 7.1 Что не меняется

`js/logic/distance.js` — **ни строки**. `haversineKm(from, to)` и `formatDistance(km)`
остаются чистой геометрией (`PRODUCT.md` 10.3). `sortByDistance(places, point)` в
`filters.js` тоже не меняется: он уже принимает точку, а не район (переименование
параметра `center` → `origin` — косметика, не контракт).

#### 7.2 Что добавляется

Одна чистая функция в `js/logic/trip.js` (модуль уже отвечает за интерпретацию `stg:trip`):

```js
// trip — из storage.getTrip(); config — из loadConfig().
// Возвращает { point: {lat,lng}|null, precision: "exact"|"area"|"none", label: string|null }.
// Чистая: без DOM, storage и location.
export function resolveOrigin(trip, config) {}
```

| `trip` | Результат |
|---|---|
| `stay.source === "gps"/"manual"` с валидной точкой | `{ point: stay.point, precision: "exact", label: stay.label ?? null }` |
| `stay.source === "spot"`, `spotId` найден в `config.areas[].spots` | `{ point: spot.point, precision: "exact", label: spot.name }` |
| `stay` пуст/не разрешается, район выбран и имеет `center` | `{ point: area.center, precision: "area", label: area.name }` |
| Район не выбран / неизвестен / `center === null` (`other`) | `{ point: null, precision: "none", label: null }` |

#### 7.3 Что это даёт по точности подписи (R12)

| `precision` | Список `#/places` | Карточка `#/place/<id>` |
|---|---|---|
| `exact` | «~0,4 км» | «~0,4 км от места проживания» |
| `area` | «~3,5 км» + плашка-подсказка «Расстояния — от центра района. Уточнить, где вы живёте» → `#/settings` | «~3,5 км **от центра района**» (сейчас — «от вашего района») |
| `none` | Расстояний нет, порядок файла, существующие плашки ([I3-15]) | Блока нет ([I3-16]) |

Формулировки — предмет утверждения владельцем (раздел 13), но **само различение
`exact` / `area` обязательно**: именно его отсутствие и превратило корректное число
в неверное обещание.

## Вывод

**Рекомендую: Вариант C** — «район остаётся логическим контекстом, точка проживания
становится отдельным необязательным значением `stg:trip.stay` с явным источником, а все
экраны получают её через одну чистую функцию `resolveOrigin(trip, config)`; в Итерации 3
точка заполняется выбором ориентира из короткого проверенного списка `config.areas[].spots`,
в Итерации 5 — геолокацией».

Почему именно он:

1. **Он чинит настоящую причину.** Проблема не в координате Ялунваня, а в том, что «район»
   используется одновременно как логический контекст и как географическая точка. C разделяет
   эти две роли — и `yalong.center`, и точка отеля остаются корректными данными, каждая в своей роли.
2. **Он ничего не ломает.** При `stay === null` поведение совпадает с сегодняшним побитово:
   те же числа, тот же порядок, те же плашки. `distance.js` и `places.json` не меняются вовсе,
   Foundation (роутинг, история, кэш, деградация) не трогается, `SCHEMA_VERSION` остаётся `1`,
   миграция данных не нужна.
3. **Он посилен по контенту.** 15–25 проверяемых ориентиров против сотен отелей в варианте A.
   Правило «не выдумываем данные» (D-18, R7) остаётся выполнимым.
4. **Он не требует от туриста координат.** Вариант B правильный по модели, но его способ ввода
   упирается в блокировку Google Maps в Китае (F-04) и смещение GCJ-02 (R-05). C оставляет B
   доступным как `source: "manual"` — но не делает его обязательным.
5. **Он не создаёт тупика для Итерации 5.** GPS дописывается в то же поле; ни один экран
   при этом не меняется. В варианте A GPS потребовал бы ломки только что выпущенного контракта.
6. **Он делает интерфейс честнее уже на первом слое.** Даже до появления `spots` подпись
   «~3,5 км **от центра района**» вместо «от вашего района» снимает ложное обещание —
   ровно то, на чём споткнулось реальное QA.

Минимальный объём, который стоит выпустить первым, — **слой C0**: поле `stay`, функция
`resolveOrigin()`, честные подписи. Он не требует ни одного решения по контенту, не меняет
ни одного числа и уже устраняет то, что пользователь воспринял как ошибку.
