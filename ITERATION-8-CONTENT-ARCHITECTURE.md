Проблема не в архитектуре, а в контенте: ни один кандидат (UNIQLO, Nike ×3, adidas, 4 мола) сейчас не имеет подтверждённых координат (`ITERATION-8-CONTENT-VERIFICATION.md`, таблица «Final ready/not-ready», все строки Shopping/Mall — «Нет»). Архитектурно готово, контентно — нет.

- **Practical rules** не требуют нового файла и нового формата вообще. `info.json` уже поддерживает произвольное число verified-карточек с `sources`/`verifiedAt`/`volatile`. 4 темы уже официально подтверждены (Drones, Coral/marine protection, Smoking, Military/sensitive photography) и могут стать обычными новыми записями `info.json` хоть сегодня — это не архитектурная задача, а контентная.
- Итог: расширение базы — это в первую очередь **добавление данных**, а не новая архитектура. Единственный по-настоящему новый элемент — файл `data/food.json` и его загрузка/рендер по образцу уже существующих «маленьких» сущностей (`contacts.json`, `phrases.json`).

## 1. Current architecture (как это работает сейчас)

### 1.1 Файлы данных и их роль

| Файл | Схема | Кто загружает | Фильтр status |
|---|---|---|---|
| `data/config.json` | `areas[]` (с `spots[]`), `categories[]`, `tags[]`, `planDayTypes[]` | `data.js: loadConfig()` | `areas` — только `verified`; `categories`/`tags`/`planDayTypes` — без статуса |
| `data/places.json` | место (9.2 PRODUCT.md): `id, status, name, addressZh, area, category, tags[], location, summary, why[], durationHours, effort, setting, price, hours?, bestTime?, tips?, sources[], verifiedAt, photos[]?, more?, story?` | `loadPlaces()` | только `verified` |
| `data/contacts.json` | `{ id, group, label, number, tel, note, sources, verifiedAt }`, **без `status`** | `loadContacts()` | нет — весь файл считается проверенным |
| `data/phrases.json` | `{ id, ru, zh, pinyin, context, source, verifiedAt }`, **без `status`** | `loadPhrases()` | нет |
| `data/info.json` | `{ id, status, title, summary, points[], volatile, sources, verifiedAt }` | `loadInfo()` | только `verified` |
| `data/plan.json` | один объект `{ meta, days[] }`, `days[].placeIds` — id из `places.json` | `loadPlan()` | нет (весь файл — контент владельца) |

Все загрузчики — чистые функции в `js/data.js`: `fetch` + promise-кэш на файл + фильтрация по `status`, где он есть. Ни один загрузчик не знает про DOM, роутинг или storage.

### 1.2 Категория `shopping` уже существует

`config.categories` (`data/config.json`): `beach, nature, culture, entertainment, market, shopping`. Иконка `🛍️` уже прописана в `CATEGORY_ICONS` (`js/views/places.js`). Сейчас в `shopping` ровно одно verified-место — `cdf-duty-free-city` (CDF, Хайтан). Это значит: **добавление нового verified shopping-места технически требует только новой записи в `places.json`**, без правок кода, config или схемы.

### 1.3 D-06 и рестораны

`PRODUCT.md` D-06: «Рестораны не включаем. Допустимы только рынки и гастроулицы» — реализовано как категория `market` в `places.json` (сейчас 1 место: `sanya-first-market`). Конкретные точки питания (рестораны, фудкорты, уличная еда) этим решением **прямо исключены** из `places.json`. Это решение владельца, оно не меняется в рамках контентного расширения без явного пересмотра (правило 0.2.2 `PRODUCT.md`).

### 1.4 «Рядом со мной» — устройство

`js/views/places.js`, блок `NEARBY_STATUS` (строки 177–422): самодостаточный участок внутри `renderPlaces()`.
- Источник точки — Geolocation API по явному тапу пользователя; точка живёт только в замыкании рендера текущего экрана, никуда не пишется (комментарий в коде явно отделяет это от `stg:trip.stay`/`resolveOrigin()`).
- Логика — `nearbyPlaces(places, origin, radiusKm)` в `js/logic/filters.js`: отфильтровывает места без пригодной координаты (`hasUsableLocation`), затем `filterWithinRadius` + `sortByDistance` (те же функции, что и у обычного списка и у сценариев Главной).
- Радиус — общая константа `NEAR_RADIUS_KM = 20` (`js/logic/filters.js`), уже используется и в `resolveOrigin()`-сценариях Главной, и здесь.
- Рендер — `renderNearbyPanel()` работает с массивом `places`, переданным в `renderPlaces()`; жёстко привязан к `places.json` только потому, что это единственный источник данных, который туда передаётся, а не по архитектурному ограничению самой функции `nearbyPlaces()`.

`resolveOrigin(trip, config)` (`js/logic/trip.js`) — чистая функция, не завязана на тип объекта: принимает точку/приоритет источника и просто возвращает точку и её точность. Она уже используется псевдо-универсально (сортировка списка мест, радиус сценариев Главной).

### 1.5 Роутинг и SW

- Роутинг — таблица regexp-маршрутов в `js/app.js` (10 с небольшим записей), каждая — `{ pattern, render, nav, fullscreen? }`. Добавление нового раздела — это новые строки таблицы + новый модуль в `js/views/`.
- `sw.js` — явный список `PRECACHE`: JS-модули, JSON, фото. Новый файл (JSON или JS) обязательно нужно вписать в массив вручную и поднять `CACHE_VERSION`.

## 2. Decision

Отвечаю по восьми пунктам задания:

### 2.1 Нужны ли `data/shopping.json` и `data/food.json`?

- **`data/shopping.json` — не нужен.** Категория `shopping` уже существует в `config.categories`, схема места уже описывает торговый объект (адрес, координаты, часы, цена, советы, источники). Отдельный файл создал бы вторую, почти идентичную схему без причины — прямое нарушение принципа «не создаём абстракций на будущее» (`PRODUCT.md` 5.4) и правила CLAUDE.md «не вводить лишние абстракции». Новые shopping-места — это записи в `places.json` с `category: "shopping"`.
- **`data/food.json` — нужен, но только если/когда владелец пересматривает D-06** (или явно вводит для еды отдельную, не подпадающую под D-06 категорию данных — см. 2.6). Причина не техническая, а продуктовая: D-06 прямо запрещает рестораны в `places.json`. Технически это маленький файл по образцу `contacts.json` — не новая архитектурная прослойка, а тот же паттерн «список записей с `sources`/`verifiedAt`», что уже трижды применён в проекте.

### 2.2 Минимальные поля shopping- и food-карточек

**Shopping — переиспользует схему места без изменений.** Единственное отличие от «типичного» места (пляж/парк) — часто есть *бренд внутри объекта* (UNIQLO внутри мола). Решение: не создавать новое поле «бренды» ради одного сценария. Если нужно упомянуть конкретный бренд внутри мола — это текст в `summary`/`why`/`tips`, как и для любого другого места. Отдельная запись `places.json` на «UNIQLO как часть три­я-Джой-Сити» не нужна, если у самого мола уже есть карточка с достаточным описанием; если нужен отдельный вход в чек-лист «Найти именно UNIQLO» — это отдельная запись места с тем же `location`, что и у мола (так же, как сейчас разные ориентиры `spots` могут указывать на близкие точки).

Минимальный набор полей shopping-записи — **тот же**, что у `places.json` (9.2 `PRODUCT.md`), обязательные поля без изменений: `id, status, name, addressZh, area, category="shopping", location, summary, why, durationHours, effort, setting, price, sources, verifiedAt`.

**Food — минимальная отдельная схема**, по аналогии с `contacts.json`/`phrases.json` (без лишних полей places.json, которые еде не нужны — `durationHours`, `effort`, `setting` не имеют смысла для точки питания):

| Поле | Тип | Обяз. | Комментарий |
|---|---|---|---|
| `id` | строка | да | латиница, дефисы, уникально — как у `places.json` |
| `status` | `draft` \| `verified` | да | нужен: в отличие от контактов/фраз, food-записи будут появляться из сырого research с неполными данными (см. верификацию — ни одна пока не «ready») |
| `name.ru` / `name.zh` | строки | да | как у места |
| `addressZh` | строка | да | для «Показать таксисту» — переиспользуется тот же компонент `taxi.js` |
| `area` | id из `config.areas` | да | тот же справочник, никакого нового |
| `kind` | `restaurant` \| `foodcourt` \| `street-food` | да | замена `category` — типы, специфичные для еды, не смешивать со `config.categories` мест |
| `location.lat/lng` | числа | нет | у части кандидатов сейчас нет подтверждённых координат (D-19 требует WGS-84, но запись имеет право быть `draft` без координаты — как и у мест) |
| `priceLevel` | `budget` \| `mid` \| `unknown` | нет | достаточно грубой оценки, а не точных чеков — цены в общепите волатильны сильнее, чем у мест |
| `hours` | строка | нет | текстом, как у мест (D-21) |
| `note` | строка | нет | 1 фраза: что это и чем отличается |
| `sources` | массив `{title, url}` | да | как везде (D-18) |
| `verifiedAt` | дата | да | как везде (D-18) |

Никаких «рейтингов», «отзывов» или «меню» полей — верификация прямо показала (`ITERATION-8-CONTENT-VERIFICATION.md`, «Review evidence quality»): ни для одного кандидата нет достаточной выборки отзывов, а нейтральность (D-04) и принцип «не выдумываем факты» (5.2) запрещают имитировать рейтинг из одного блога.

### 2.3 Что переиспользовать из places.json/schema/helpers/UI

- **Схему целиком** — для shopping (без изменений).
- **`js/logic/distance.js`** (`haversineKm`, `formatDistance`) — универсальны, работают с любыми `{lat, lng}`, не завязаны на `places.json`.
- **`resolveOrigin()`** (`js/logic/trip.js`) — уже независим от типа объекта, возвращает только точку и точность; годится для food без изменений.
- **`nearbyPlaces()`/`filterWithinRadius()`/`sortByDistance()`** (`js/logic/filters.js`) — не привязаны к полю, специфичному для мест (`effort`, `setting`), используют только `place.location`; можно вызвать на массиве food-записей как есть, если у записи есть `location` в том же формате.
- **`taxi.js`** (общий экран «Показать таксисту») — уже общий компонент, используется и местами, и «Под рукой» (адрес проживания), и фразами. Подходит food/shopping без изменений: нужен только `addressZh` + `name`.
- **`js/views/place.js`** как *образец* устройства карточки (порядок блоков, фото/`more`/`story`, кнопки) — для shopping можно использовать без изменений (это те же места). Для food — не переиспользовать сам компонент 1-в-1 (в карточке места есть поля, которых у food нет: `effort`, `durationHours`, «Добавить в мой план»), а сделать отдельный, короткий `views/food.js` по аналогии с `views/handy.js` (простой список + переход на полноэкранный `taxi.js`).
- **`CATEGORY_ICONS`** — для food не подходит (у еды нет `config.categories`), нужна отдельная маленькая карта иконок по `kind`.

### 2.4 Интеграция с «Рядом со мной»

**Shopping** — уже работает: shopping-места входят в `places.json`, значит автоматически участвуют в существующем «Рядом со мной» без единой правки кода, как только у них появятся подтверждённые координаты.

**Food** — реалистичный минимум: **отдельная, вторая кнопка/панель «Еда рядом», не смешанная с существующей «Рядом со мной» для мест.** Причины:
- `nearbyPlaces()` уже принимает произвольный массив с `location` — техническую часть переиспользовать можно тем же вызовом на `food`-записях.
- Но UI-панель `NEARBY_STATUS` в `places.js` сейчас рендерит `renderPlaceRow()`, которая читает поля мест (`durationHours`, `effort`, `category`) — эти поля у food нет. Смешивать список получится только ценой добавления условной логики внутри уже плотного `places.js`, что усложнит код без явной пользы.
- Продуктово смешение тоже не нужно: «Рядом со мной» на вкладке «Места» ищет *куда пойти*, а еда — отдельный сценарий («что поесть рядом»), у него, вероятно, будет собственная точка входа (например, с Главной в состоянии «В поездке», рядом с «Под рукой» — решение уже не архитектурное, а UX, и не входит в этот документ).
- Минимальная реализация (когда будет принято решение по контенту): свой `views/food.js`, свой маленький рендер результатов, тот же `getCurrentPosition()`/`nearbyPlaces()` — не через дублирование кода `places.js`, а через вынос `getCurrentPosition()` и блока `NEARBY_STATUS`-состояний в `logic/geo.js` (единственный кандидат на новый `logic`-модуль во всей записке — переиспользуется двумя экранами, поэтому оправдан).

### 2.5 Расширять ли `config.json`?

**Не обязательно для первого шага.** `categories`/`tags`/`areas` уже покрывают shopping. Единственный реальный кандидат на расширение — **новый `config.areas` для делового района Дун'ань**, если в него пойдёт UNIQLO-мол (`ITERATION-8-NEXT-CONTENT-RESEARCH.md`, «нужно продуктовое решение: новый район или часть `city`»). Это узкое, точечное расширение существующего справочника (одна новая запись `areas[]`), а не архитектурное изменение — но именно продуктовое решение владельца, не техническое. Для food `config.json` расширять не нужно вообще: `area` берётся из существующего справочника, `kind` — новый маленький enum внутри самой `food.json`-схемы (аналогично тому, как `contacts.json` хранит свой `group` не в `config.json`).

### 2.6 Как не смешивать рестораны с `places.json`, учитывая D-06

Механически — двумя барьерами:
1. **Отдельный файл** `data/food.json`, отдельный загрузчик `loadFood()` в `data.js` — физически другая структура данных, не тот же массив, что `places.json`.
2. **Отдельная категория данных в `config.categories` не заводится** — если food попадёт в `places.json` через `category: "food"` завтра по недосмотру, это будет прямым нарушением D-06. Явная защита — code review / чек-лист валидации: *в `places.json` не может быть `category`, обозначающей еду; все food-записи живут только в `food.json`*. Это не техническое ограничение (JSON Schema в проекте нет и не планируется — MVP, D-23), а **договорное правило**, которое стоит явно зафиксировать в `PRODUCT.md` при принятии решения о food-слое, если/когда D-06 будет переформулировано (например: «D-06: рестораны не включаются в `places.json`; допустимы в отдельном `data/food.json`»).

### 2.7 Источники, дата проверки, уровень уверенности

Уже есть паттерн — `sources[]` + `verifiedAt`, применяется во всех файлах (D-18). Для shopping/food ничего нового изобретать не нужно: та же пара полей. **Уровень уверенности** — новая идея, которой в проекте пока нет ни у одного типа контента. Судя по `ITERATION-8-CONTENT-VERIFICATION.md` (явные пометки «READY» / «DO NOT PUBLISH YET» / «Нет — не хватает координат»), уровень уверенности уже неявно выражается через **сам факт наличия `status: "verified"` vs `"draft"`** — черновик и есть «недостаточно уверенности для показа пользователю» (D-18). Отдельное поле `confidence` не нужно: `status` уже кодирует ровно это разделение, и добавление второго измерения уверенности усложнило бы модель без пользы (принцип «не создаём абстракций на будущее»). Если нужно различать «этикет, не закон» от «официальное правило» (как у Nanshan) — это не про уверенность в факте, а про **тип нормы**; решается текстом внутри карточки (явная пометка в `points[]`/`summary`), как и предписывает сама верификация («публиковать только с явной пометкой „этикет“»), а не новым полем схемы.

### 2.8 Минимальные изменения UI/роутинга/SW

**Practical rules (4 темы)** — минимум изменений вообще:
- Изменения: 4 новые записи в `data/info.json` (тот же формат, что у 6 существующих карточек). Ничего в коде менять не нужно — `js/views/info.js` уже рендерит произвольное число verified-карточек.
- SW: `data/info.json` уже в `PRECACHE`, новая версия файла подхватится сама при следующем `CACHE_VERSION`. Нужно только поднять версию.
- Роутинг: не меняется — маршрут `#/info/<id>` уже общий для всех карточек.

**Shopping** — минимум изменений:
- Данные: новые записи в `places.json` с `category: "shopping"` (когда появятся подтверждённые координаты).
- Код: **ноль изменений**, если места используют существующие поля. Опционально — новая иконка/более точный emoji под `shopping`, но `🛍️` уже есть.
- Роутинг: не меняется — `#/place/<id>` уже общий.
- SW: только новые фото (если есть) в `PRECACHE`; `places.json` уже там.

**Food** — самый крупный, но всё ещё небольшой набор изменений:
- Новый файл `data/food.json`.
- Новая функция `loadFood()` в `js/data.js` (копия `loadPlaces()`/`loadContacts()` по образцу, ~10 строк).
- Новый модуль `js/views/food.js` (список + переход на `taxi.js`), по образцу `views/handy.js`.
- Новый маршрут в `js/app.js` (например, `#/food`, `#/food/<id>`) — 1–2 строки в таблицу `routes`.
- Точка входа в навигации: где именно показывать ссылку на еду — продуктовый вопрос (см. открытые вопросы ниже), не входит в этот документ, но с точки зрения кода это одна ссылка в существующем экране (`home.js`, `info.js` или отдельный пункт нижней панели — **пятой вкладки по решению 8.1 `PRODUCT.md` нет**, поэтому вероятнее вложенный экран, как «Под рукой»).
- Опционально `logic/geo.js`, если food получает свою кнопку «рядом» (см. 2.4).
- SW: `data/food.json` + новый `js/views/food.js` (+ `logic/geo.js`, если он появится) — в `PRECACHE`, `CACHE_VERSION` поднимается.

### 2.9 Что сделать без усложнения продукта и без новой архитектурной прослойки

- Не заводить `data/shopping.json` — использовать `places.json` как есть.
- Не заводить общий «универсальный слой POI» (мест+еды+шоппинга в одной абстрактной модели) — три схожих, но разных по природе типа контента (турместо / точка питания / практическое правило) не требуют общего родителя; попытка объединить их сейчас — абстракция на будущее, прямо запрещённая CLAUDE.md и `PRODUCT.md` 5.4.
- Не добавлять `confidence`/рейтинги — `status` уже делает эту работу.
- Не трогать `resolveOrigin()`/`distance.js`/`filters.js` — они уже достаточно общие, чтобы принять food без изменений сигнатур.
- Practical rules вообще не требуют новой архитектуры — это чистое расширение существующего `info.json`.

## 6. Implementation sequence

Порядок ниже — предлагаемая последовательность **небольших batch'ей**, каждый — самостоятельно проверяемый и не блокирующий следующий. Ни один batch сам по себе не требует остальных.

**Batch A — Practical rules (низкий риск, ноль архитектуры)**
1. Добавить 4 verified-записи в `data/info.json`: Drones, Coral/marine protection, Smoking, Military/sensitive photography (данные — из `ITERATION-8-CONTENT-VERIFICATION.md`, раздел «Final ready/not-ready table»).
2. Опционально — `draft` или текстовая пометка для Nanshan etiquette, если решено показывать как «местная практика».
3. Поднять `CACHE_VERSION` в `sw.js` (файл `data/info.json` уже в `PRECACHE` — новых строк не требуется).
4. Проверка: `#/info` показывает новые карточки, источники и дата проверки на месте, офлайн работает (см. раздел «Validation» CLAUDE.md).

**Batch B — Shopping, 1 объект (низкий риск, контент, не архитектура)**
1. Выбрать один кандидат с наибольшей вероятностью подтвердить координаты (по выводу research — `三亚国际购物中心` или `大东海国际购物中心`, оба содержат официально подтверждённый Nike).
2. Получить и подтвердить координаты (не входит в этот документ — требует нового research-прохода, вне текущего задания).
3. Решить, к какому `area` относится объект (`city` или новый — только если это Дун'ань).
4. Добавить запись в `places.json` со `status: "verified"` только после устранения всех «НУЖНО ПРОВЕРИТЬ».
5. Добавить фото в `PRECACHE`, если есть (по образцу Итерации 7).
6. Проверка: место появляется в `#/places` с фильтром «Покупки», попадает в «Рядом со мной», если в радиусе; работает «Показать таксисту».

**Batch C — Food, схема и загрузчик (архитектурный минимум, без контента)**
1. Создать `data/food.json` — пустой массив или 1 `draft`-запись для проверки формата.
2. Добавить `loadFood()` в `data.js`.
3. Добавить `data/food.json` в `PRECACHE`.
4. Без UI — это чисто инфраструктурный шаг, можно проверить только через консоль/DevTools (`loadFood()` возвращает ожидаемый массив).

**Batch D — Food, минимальный UI (после решения владельца о точке входа)**
1. `views/food.js` — список food-записей по образцу `views/handy.js`.
2. Маршрут(ы) в `app.js`.
3. Ссылка на экран — из `home.js` (сценарий «В поездке») или из `info.js`/«Под рукой» — конкретика зависит от продуктового решения (см. открытые вопросы).
4. Наполнение 1–2 verified food-записями после отдельного research-прохода по координатам (Diadia Coconut Chicken, `东榕美食广场` — оба помечены «Нет» в верификации, нужны доп. данные).
5. Проверка: список открывается офлайн, «Показать таксисту» работает, `#/food` не ломает навигацию/Back.

**Batch E — Food + «рядом» (опционально, только если появится ≥2–3 verified food-записи с координатами)**
1. Вынести `getCurrentPosition()` и общие геолокационные состояния из `places.js` в `logic/geo.js`.
2. `places.js` переиспользует `logic/geo.js` без изменения поведения (рефакторинг, не новая функциональность — проверить, что «Рядом со мной» для мест не сломалось).
3. `views/food.js` использует тот же `logic/geo.js` + `nearbyPlaces()` на food-массиве.

## 7. Risks / open questions

Технических рисков в самой архитектуре немного — основной риск проекта сейчас контентный, не архитектурный:

1. **Ни одна shopping/food-запись не готова к публикации** (0 «ready» в `ITERATION-8-CONTENT-VERIFICATION.md`) — нужен ещё один research-проход именно за координатами, прежде чем Batch B/D дадут пользователю что-то новое. Без этого архитектура готова, но пустая.
2. **D-06 требует явного решения владельца**, прежде чем `data/food.json` вообще получит смысл — это открытый продуктовый вопрос, не может быть решён implicitly через архитектурный документ (правило 0.2.2 `PRODUCT.md`).
3. **Дун'ань не совпадает ни с одним `config.areas`** — если UNIQLO-мол окажется единственным привлекательным shopping-кандидатом, придётся решать: новый район или часть `city`. Точечное решение, не блокирует остальную архитектуру.
4. **Точка входа в food с точки зрения UX** не определена этим документом (сознательно, чтобы не выходить за рамки архитектурного анализа) — где именно в навигации появляется ссылка на еду, решается отдельно, скорее всего по аналогии с «Под рукой» (вложенный экран Главной/Справки, без пятой вкладки, D-07).
5. **Регламент перепроверки (D-22)** для shopping/mall-контента, вероятно, должен быть чаще, чем 6 месяцев для обычных мест — сама верификация отмечает высокую волатильность состава арендаторов; это скорее пункт для будущего решения владельца, чем для этого документа.
6. **Практическое правило vs этикет (Nanshan)** — единственный содержательный, не архитектурный риск: если карточку опубликовать без явной пометки «не официальное правило», это нарушит принцип 5.2 («не выдумываем факты о правилах»).
7. **Confidence-как-отдельное-поле была явно отклонена** в этом анализе (2.7) в пользу существующего `status`; если в будущем появится контент с промежуточным уровнем доверия (не draft, не полностью verified) — стоит вернуться к этому вопросу отдельно, а не решать его сейчас на пустом месте.

1. **Batch A** — Practical rules → `data/info.json` (4 записи), поднять `CACHE_VERSION`.
